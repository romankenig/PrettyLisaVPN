# PrettyLisaVPN WireGuard node automation

This Ansible playbook configures a dedicated Ubuntu 24.04 VPN data-plane node. It installs Ubuntu's official `wireguard` package, creates `wg0`, enables IPv4 forwarding, configures UFW routing and NAT, and enables `wg-quick@wg0` at boot. It does not install the Backend, PostgreSQL, Valkey, Caddy, Docker, a node agent, or static client peers. It does not call the DigitalOcean API.

The separately deployed minimal control agent is documented in [vpn-node-agent/README.md](../../vpn-node-agent/README.md) and uses `playbooks/vpn-node-agent.yml`. The base WireGuard playbook remains independent of it.

The server private key is generated by `wg genkey` on the Droplet as `/etc/wireguard/server_private.key`, mode `0600`. It is never returned to Ansible or placed in `wg0.conf`. The public key is `/etc/wireguard/server_public.key`, also mode `0600`; an operator may read that public value with `sudo` when registering control-plane metadata.

## Prerequisites and firewall plan

Apply [the secure node baseline](../../docs/digitalocean-vpn-node-baseline.md) first. Confirm key-only `vpnadmin` SSH and passwordless sudo in a separate session, keep that session open during deployment, and confirm UFW is active. The role deliberately refuses to enable an inactive UFW because it cannot safely infer the administrator's SSH source network.

Before deployment, attach a DigitalOcean Cloud Firewall to the Droplet and ensure these inbound rules exist:

| Protocol | Port | Source | Purpose |
| --- | ---: | --- | --- |
| TCP | 22 | trusted administrator IP/CIDR | SSH |
| UDP | 51820 (or configured port) | All IPv4 (`0.0.0.0/0`) | VPN clients |

Allow outbound TCP, UDP, and ICMP to IPv4 destinations as required by the baseline. IPv6 VPN forwarding is not configured. Do not open HTTP, HTTPS, PostgreSQL, Valkey, Docker API, or application ports. DigitalOcean Cloud Firewall is configured in the control panel; this playbook has no API credentials or provider dependency.

Expected host firewall additions are UDP/51820 ingress, routed traffic from `wg0`/`10.77.0.0/16` to the detected public interface, and a matching `MASQUERADE` rule. Existing SSH rules are preserved. UFW logging remains off so packet addresses and user traffic destinations are not logged.

## Inventory and variables

From the repository root, copy the safe inventory example to the ignored production filename:

```powershell
Copy-Item infra/ansible/inventories/production/hosts.example.yml infra/ansible/inventories/production/hosts.yml
```

Do not add a private key to the inventory or repository. Defaults are in `group_vars/vpn_nodes.yml`:

```yaml
wireguard_client_subnet: 10.77.0.0/16
wireguard_gateway_cidr: 10.77.0.1/16
wireguard_listen_port: 51820
wireguard_public_interface: null  # auto-detect the default IPv4 interface
wireguard_public_ipv4: null       # auto-detect the default route's source IPv4
```

The role checks the selected interface and source address against `ip -4 route get 1.1.1.1`; it never assumes `eth0`. The gateway prefix must describe exactly the configured client subnet. Override values with reviewed inventory variables or `--extra-vars`; do not put secrets there.

## Deploy

Install Ansible on an administration machine or in WSL. From `infra/ansible`, verify connectivity and show the proposed changes first:

```bash
cd infra/ansible
ansible vpn_nodes -m ping --private-key ../../keys/github-actions-development
ansible-playbook playbooks/wireguard-node.yml --private-key ../../keys/github-actions-development --check --diff
ansible-playbook playbooks/wireguard-node.yml --private-key ../../keys/github-actions-development
```

For a different key, pass its path without copying it into Git. Keep the pre-existing SSH session open and verify a new key-only SSH connection after applying the firewall change.

## Verify

From the administration machine:

```bash
ssh -i keys/github-actions-development -o IdentitiesOnly=yes vpnadmin@204.48.17.50
```

On the Droplet:

```bash
sudo wg show wg0
sudo ip -brief address show wg0
sudo systemctl is-enabled wg-quick@wg0
sudo systemctl is-active wg-quick@wg0
sysctl net.ipv4.ip_forward
sudo ufw status verbose
sudo ufw status numbered
ip -4 route show default
ip -4 route get 1.1.1.1
sudo iptables -t nat -C POSTROUTING -s 10.77.0.0/16 -o "$(ip route show default | awk 'NR==1 {print $5}')" -j MASQUERADE
sudo iptables -L ufw-user-forward -v -n -x --line-numbers
sudo iptables -t nat -L POSTROUTING -v -n -x --line-numbers
sudo nft list ruleset
sudo stat -c '%a %U:%G %n' /etc/wireguard /etc/wireguard/server_private.key /etc/wireguard/server_public.key /etc/wireguard/wg0.conf
sudo grep -c '^\[Peer\]' /etc/wireguard/wg0.conf
sudo ss -lunp | grep ':51820 '
```

Expected results: `wg0` has `10.77.0.1/16`; `wg-quick@wg0` is enabled and active; forwarding is `1`; UFW is active with logging off and preserves SSH; UDP/51820 is allowed only over IPv4 on the resolved public interface/address; the forwarding policy remains `DROP`; the only VPN forward allow is `10.77.0.0/16` from `wg0` to the resolved egress interface; and the NAT check succeeds. Directory mode is `700`, key/config modes are `600`; peer count is `0`. `wg show` prints the server **public** key and no peers. Never print or copy `server_private.key`.

The counter commands initially show zero packets because this playbook intentionally installs no peers. After a future node agent adds an ephemeral test peer, capture counters before and after sending traffic through that test tunnel:

```bash
sudo wg show wg0 transfer
sudo iptables -L ufw-user-forward -v -n -x --line-numbers
sudo iptables -t nat -L POSTROUTING -v -n -x --line-numbers
# Send IPv4 traffic through the temporary test tunnel, then repeat all three commands.
sudo wg show wg0 transfer
sudo iptables -L ufw-user-forward -v -n -x --line-numbers
sudo iptables -t nat -L POSTROUTING -v -n -x --line-numbers
```

The peer receive/send byte counts and both matching packet/byte counters must increase. Confirm the test client's observed public IPv4 is the Droplet address, then remove the ephemeral peer. Do not add a static production peer for this verification. Counter inspection records only aggregate rule/peer totals; do not enable packet logging or capture DNS queries, URLs, destinations, or packet contents.

## Reboot verification

Keep Recovery Console available, then:

```bash
sudo reboot
```

Reconnect and verify persistent state:

```bash
ssh -i keys/github-actions-development -o IdentitiesOnly=yes vpnadmin@204.48.17.50
sudo systemctl is-active wg-quick@wg0
sudo wg show wg0
sudo ip -brief address show wg0

systemctl --failed
```

## Rollback and recovery

Run rollback from the preserved SSH session or DigitalOcean Recovery Console. Capture the numbered UFW rules first because their numbers vary:

```bash
sudo systemctl disable --now wg-quick@wg0
sudo ufw status numbered
sudo ufw delete allow in on eth0 proto udp from 0.0.0.0/0 to 204.48.17.50 port 51820
sudo ufw route delete allow in on wg0 out on "$(ip route show default | awk 'NR==1 {print $5}')" from 10.77.0.0/16
sudo sed -i '/# BEGIN ANSIBLE MANAGED PRETTYLISAVPN WIREGUARD NAT/,/# END ANSIBLE MANAGED PRETTYLISAVPN WIREGUARD NAT/d' /etc/ufw/before.rules
sudo rm -f /etc/sysctl.d/90-prettylisavpn-wireguard.conf /etc/wireguard/wg0.conf
sudo sysctl -w net.ipv4.ip_forward=0
sudo ufw reload
```

The ingress deletion above is exact for the first node. For another node, substitute the interface and public IPv4 shown by `ip -4 route get 1.1.1.1`.

The key files are intentionally retained so rollback is recoverable. After confirming that the key is no longer registered or needed, destroy it only with an explicit operator decision:

```bash
sudo rm -f /etc/wireguard/server_private.key /etc/wireguard/server_public.key
```

Remove the UDP rule from the DigitalOcean Cloud Firewall separately. Preserve TCP/22. If access is lost, open Droplet → Settings → Recovery Console, log in or reset the root password, run the rollback commands, verify `sshd -t`, `systemctl restart ssh`, and `ufw status`, then test key-only SSH before closing the console. The broader recovery procedure is in the secure node baseline.

Rollback does not remove the Ubuntu WireGuard package because package removal is unnecessary and makes recovery slower. No command enables traffic-content, DNS-query, URL, destination, or packet logging.
