## D–E. Firewall and forwarding

The exact commands are generated by `render.py` into `routing.sh`, printed before
Ansible applies them, and persisted by `prettylisa-profile-routing.service`.
No global policy changes, rule flushing, SSH changes or UFW activation occurred.
Only enabled profile listeners receive new rules. Existing NYC policies remain.
Netcup retains its previous host policy; TCP/8443 has an explicit backend-only
allow followed by deny, persisted by `prettylisavpn-agent-firewall.service`.
Agent mTLS and token authentication are both required. SSH/22 stays available.

Per tunnel: `ip_forward=1`, source-subnet forwarding to eth0, established return
forwarding, MASQUERADE on eth0 and INPUT denial from the tunnel to node services.
MTU is 1280. Subnets: wg0 10.77.0.0/16, Netcup OpenVPN 10.78.0.0/24,
NYC OpenVPN/stunnel 10.79.0.0/24, MASQUE 10.80.0.0/24.
DNS uses 1.1.1.1/1.0.0.1 through the VPN forwarding path; there is no public DNS
forwarder on the node. The probe independently verifies the configured DNS path.

Firewall reloads require restarting the profile routing service and, on Netcup,
the agent firewall service. Incorrect tunnel interfaces can block management;
physical-interface misuse and agent port equal to SSH are rejected. Changed
manifests require a reviewed cutover; the additive deployment role refuses to
silently leave obsolete services/rules behind.

## F. Backend capability boundary

Migration `0017_profile_evidence` adds `vpn_nodes.deployed_profiles` JSONB.
Each profile records protocol, transport, port, encryption, obfuscation, free
availability, enabled state, health status, configuration digest and evidence.
`verified_profiles(now)` exposes only matching successful evidence. Imports must
be made within 24 hours of testing. Stored evidence records the demonstrated
configuration; it is not a live Internet guarantee or a daily expiration of the
working service. Failed DNS/HTTPS/routes/egress, changed revision, disabled profiles
and missing evidence exclude a profile. A socket or handshake alone is never
enough. Legacy declarations are not automatically promoted to E2E_VERIFIED.

The trusted import command accepts operator reports, not unsigned reports from
arbitrary clients. It updates only capability metadata, preserving concurrent
node health changes. Existing app session issuance remains WireGuard-only;
TLS/QUIC account credential delivery and new selection policies are not added.
Migrated nodes return an explicit verified WireGuard UDP/51820 + NONE candidate,
so local legacy settings cannot redirect it to Netcup's MASQUE UDP/443. Mismatched
or failed evidence makes the migrated node ineligible for new sessions. Live
node-health eligibility and per-connection client verification still apply. Legacy
nodes retain existing behavior. Old clients without candidate negotiation need
upgrading or matching local configuration; Netcup clients must reconnect because
the reset replaced its WireGuard key. This changes no node ranking or fallback.
The imported live catalog was read back from the backend:
[capability audit](reports/backend-capabilities-20260923.jsonl).

## G. Repeatable manual verification

Run as root on the corresponding node:

```sh
systemctl is-active wg-quick@wg0 prettylisa-profile-routing prettylisa-profile-wg-simple
systemctl is-enabled wg-quick@wg0 prettylisa-profile-routing prettylisa-profile-wg-simple
ss -H -lnut 'sport = :51820 or sport = :5443 or sport = :443'
sysctl -n net.ipv4.ip_forward
ip link show wg0
iptables -t nat -C POSTROUTING -s 10.77.0.0/16 -o eth0 -m comment --comment pl-wg0 -j MASQUERADE
iptables -C FORWARD -i wg0 -o eth0 -s 10.77.0.0/16 -m comment --comment pl-wg0 -j ACCEPT
journalctl -u prettylisa-profile-wg-simple -n 30 --no-pager
# NYC:
systemctl is-active prettylisa-profile-ovpn-tls prettylisa-profile-ovpn-tls-tls
ss -H -lnt 'sport = :1195'
journalctl -u prettylisa-profile-ovpn-tls -u prettylisa-profile-ovpn-tls-tls -n 30 --no-pager
iptables -t nat -C POSTROUTING -s 10.79.0.0/24 -o eth0 -m comment --comment pl-plovpntls -j MASQUERADE
# Netcup:
systemctl is-active prettylisa-profile-ovpn prettylisa-profile-masque prettylisavpn-node-agent prettylisavpn-agent-firewall

iptables -C INPUT -s 95.140.152.42/32 -d 5.181.49.183 -p tcp --dport 8443 -j ACCEPT
iptables -C INPUT -d 5.181.49.183 -p tcp --dport 8443 -j DROP
```

For packet arrival counts from this trusted tester only (no payload output/file):
`tcpdump -i eth0 -n -c 10 'host 95.140.152.42 and udp port 443' >/dev/null`.
Replace the transport/port for other profiles. Do not inspect/log production user
traffic. Logs and configs must not be published wholesale.

Follow the exact standalone Docker build/connect commands in [README](README.md).
The runner works on another Linux VPS, region, ISP or trusted cloud VM with
Docker/TUN/NET_ADMIN and outbound access to the chosen transport. Transfer only

## J. Unsupported/unverified combinations and remaining work

NYC MASQUE remains disabled/UNTESTED because its UDP/443 serves the existing VPN.
No port migration was necessary on empty Netcup, where MASQUE now works.
NYC plain OpenVPN and Netcup OpenVPN-over-stunnel remain disabled/UNTESTED because
each conflicts with the selected TCP/443 variant. Each combination is verified
on the other node, but that does not confer support on this node.

IPv6, browser extension proxy delivery, TLS/QUIC credentials tied to user sessions,
cross-platform executable packaging, production CA lifecycle/revocation and
periodic external evidence renewal are not implemented. The custom MASQUE TUN
adapter needs further security review before broad production enrollment; mature
TLS/QUIC libraries do not imply an audit of the entire application adapter.
The first-party simple packet wrapper is still experimental framing and adds no
cryptographic security. No fallback or new Autopilot work was performed.
