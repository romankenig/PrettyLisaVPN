# Разделение трафика

Backend 0.23.0 → 0.24.0 (миграция 0037), Android 0.15.3/code31 →
0.16.0/code32, Windows 0.18.1 → 0.19.0, managed engine 0.3.0 → 0.4.0.
Новая возможность; существующие API подключения и полный туннель совместимы.

На главной доступны весь трафик, только выбранные сервисы через VPN и все,
кроме выбранных сервисов, через VPN. Кнопка «Выбрать сервисы» открывает отдельное
модальное окно с двумя независимыми списками. Маски вводятся вручную или
добавляются вместе с выбранным сервисом. Точное имя не включает поддомены;
`*.example.com` включает поддомены, но не `example.com`. IDN преобразуется в
ASCII. Протоколы URL, пути, IP-адреса, порты и произвольные регулярные выражения
не принимаются; максимум 256 результирующих масок на режим.

Сохранение изменений останавливает активное/начинающееся соединение и ждёт
подтверждения очистки. Самостоятельного переподключения нет. Следующая ручная
попытка получает снимок правил. Списки хранятся только на устройстве. Изменение
серверного каталога не переписывает действующие правила без сохранения выбора.

PostgreSQL хранит каталог `traffic_services`, включая YouTube и Instagram,
идентификаторы иконок и все доменные маски. Аутентифицированный
`GET /vpn/traffic/services` читает его через application service/repository;
контроллер не занимается маршрутизацией. Клиенты рисуют собственные векторные
иконки по известным ключам; сервер не присылает исполняемую разметку.
Пользователь видит полный набор доменов, в том числе общие CDN: `fbcdn.net`
может обслуживать другие сервисы Meta. Каталог обновляется оператором в БД.

Движок применяет единые правила к каждому реализованному протоколу и его
варианту с посредником. При разделении WireGuard использует уже имеющийся
WireGuard outbound управляемого движка, с тем же серверным доступом и локальным
закрытым ключом. Полный WireGuard сохраняет прежний native adapter.
DNS перехватывается внутри TUN: временные адреса FakeDNS сохраняют соответствие
домену; реальные запросы DNS идут через VPN. Трафик выбранного домена и прочий
трафик получают разные выходы. Для ранее закэшированных адресов используются
HTTP/TLS/QUIC metadata sniffing без расшифровки содержимого, сохранения или логов.
Прямой выход использует защищённые системные сокеты вне TUN. Нераспознанный
трафик следует правилу режима; незнакомые FakeDNS-адреса блокируются.

Проверка VPN и API `api.prettylisavpn.com` всегда проходят через VPN, независимо
от пользовательского списка. Прямой интернет не может подтвердить туннель.
IPv6 остаётся блокированным, как в прежних managed-профилях; эта задача не
добавляет серверный IPv6. Приложения со своим зашифрованным DNS и скрытым SNI
могут не раскрывать домен: для надёжного выбора по маске им нужен системный DNS.
После отключения временные DNS-адреса имеют короткий TTL; длительное собственное
кэширование приложения требует обновления соединений приложения.

Основание конфигурации: закреплённый исходный код Xray и документация
[FakeDNS](https://xtls.github.io/en/config/fakedns.html),
[routing](https://xtls.github.io/en/config/routing.html).
Никакие пользовательские DNS-запросы, назначения, URL или пакеты не записываются.

Проверки: API/auth и границы каталога, миграция/SQL-проекция, независимое хранение
двух списков, IDN/маски, создание профилей всех методов закреплённым core,
реальные loopback-потоки через оба выхода и FakeDNS, native Windows и Android UI.
Приёмка на реальных серверах, полный CI, product/build SHA и артефакты должны
быть зафиксированы в PR после проверок. Эта запись не подтверждает выкладку.
