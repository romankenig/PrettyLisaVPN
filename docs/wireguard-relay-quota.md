## Постоянный маршрут

Клиент → `timeweb-rus-001` → выбранный DE/US → интернет. RU остаётся на всё время
сеанса и пересылает зашифрованные UDP-пакеты; WireGuard завершается на DE/US.
RU не получает закрытых ключей клиента и не расшифровывает пользовательский трафик.
Это дополнительный маршрут WireGuard, без маскировки протокола. Доступность из
конкретной сети владельца требует ручного теста; handshake не считается успехом.

Оба клиента сначала вызывают реальный `wireguard`, после подтверждённой очистки —
`wireguard_relay`, затем 13 оставшихся трёхсекундных пустышек. Видны текущая попытка,
предыдущий неудачный способ и действующий способ. Успех требует HTTPS через туннель
с ожидаемым IP выхода. Android остаётся одним APK с прежним движком; Windows
использует прежнюю интеграцию с установленным официальным WireGuard.

## Выдача и отзыв

1. `POST /vpn/wireguard/sessions` принимает необязательный `method`, по умолчанию
   `wireguard`. Старые клиенты совместимы. Идемпотентность включает метод.
2. Аккаунт и roster блокируются в согласованном порядке. Выбираются доступные выход
   нужной страны/тарифа и INTERMEDIATE. Клиентский адрес и уникальный UDP-порт RU
   20000–29999 закрепляются до подтверждённого удаления, включая неудачные попытки.
3. Worker выдаёт peer на выходе, затем фиксированный DNAT/SNAT на RU. Только оба
   подтверждения дают READY. Ключ, адрес и ожидаемый IP — выхода; endpoint — RU.
4. Оба 180-секундных доступа продлевает серверный worker, не HTTP heartbeat телефона.
   UTC deadline в firewall действует при остановке worker/таймера. Root-only journal
   записывается до изменения сети. Проверки аккаунта, устройства, тарифа сохраняются.
5. Отзыв на RU сначала блокирует поток, затем убирает NAT/conntrack и журнал. Worker
   пытается удалить оба доступа даже при отказе одного узла. Неопределённый результат
   сохраняет порт и время зарезервированными для повторной очистки.

Ansible и Ubuntu helper управляют узлами. Регулярные процессы работают на основном
сервере и в node systemd timers независимо от Codex. API не передаёт VPN-трафик.
Посещения, DNS-запросы, содержимое пакетов и закрытые ключи не журналируются.
Семантика удаления сверена с [Netfilter manual](https://netfilter.org/projects/conntrack-tools/conntrack-manpage.html).

## Группы и мониторинг

`PATCH /admin/nodes/{uuid}` меняет name/group только с admin-token. Смена группы
при неочищенном доступе запрещена. `is_available_for_free` синхронизирован для старых
контрактов; миграция выводит исходные группы из этого флага.
Целевые имена/группы: `netcup-de-001`, `digocean-us-001` — FREE;
`timeweb-rus-001` — INTERMEDIATE. PREMIUM пока пустая группа.

INTERMEDIATE исключены из стран/AUTO и прямой выдачи для всех тарифов. Внутренние
изолированные проверки могут использовать их как источник и цель. Расписание
остаётся распределённым и автоматически включает новые узлы. Дашборд показывает
три сводки, подписи и фильтр группы, затем отдельного сервера. Успешность группы
взвешена по часам наблюдений; пустая группа показывает «—». Нагрузка RU включает
неистёкшие relay reservations консервативно, не означает передачу пакетов каждым
клиентом. Плановая проверка WG узла и разовая проверка полного relay-маршрута —
разные доказательства.

## Остаток Free и разовый сброс

`free_seconds_remaining` по-прежнему означает бюджет для нового сеанса.
`free_seconds_usable` включает неиспользованную часть READY reservations всех
устройств аккаунта; `free_running_sessions` задаёт скорость локального отсчёта.
`/me` содержит момент наблюдения и следующий UTC reset. Клиенты обновляют баланс
при входе Home, смене VPN-состояния и каждые 30 секунд; отсчёт — раз в секунду.
Недоступные данные — «—»; платные планы не показывают лимит. Сервер определяет
допуск и окончание сеанса, локальный счётчик только отображает остаток.

Закрытый CLI `python -m prettylisavpn.client_vpn.reset_quota --email EMAIL --request-id UUID`
делает один reset за UTC-день, только Free и после удаления прежних доступов.
Повтор UUID идемпотентен; история не удаляется, меняется граница учёта аккаунта/дня.
Сброс `kenromka@yandex.com` выполняется отдельно от миграции, с результатом в PR.

## Проверка и откат

Проверяются PostgreSQL reservations/cleanup/группы/квота, права нового API, порядок
клиентских адаптеров и текущее native Windows UI со счётчиком. Android CI
`force_relay=true` блокирует UDP/51820 только на одноразовом runner и требует
перехода direct → relay, HTTPS/egress и пяти минут deep Doze. Каждая реальная
попытка использует свежий одноразовый аккаунт; максимум три попытки до разбора.
Личный телефон и маршруты рабочего Windows-компьютера этими тестами не меняются.

**BREAKING для rollback схемы/старого backend:** старый worker не управляет relay,
а старый backend не заполняет обязательный group. Сначала закрыть новую выдачу,
дождаться удаления обоих концов relay leases, сохранить аудит reset, downgrade
до 0030, затем запускать прежний backend. Downgrade 0031 откажет при неочищенном
relay и отключит INTERMEDIATE, чтобы старый backend не предложил RU платным
пользователям. Downgrade 0032 убирает reset и может вернуть прежний расход дня.
Сохранить три SSH inventory entries, pinned host keys, WireGuard keys и immutable
release. Старые клиенты можно откатить отдельно: они используют прямой WireGuard.
