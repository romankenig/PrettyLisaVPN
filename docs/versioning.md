# Версии компонентов и порядок изменений

## Область действия

Это основной документ о версиях PrettyLisaVPN. Правила обязательны для будущих
изменений; краткая инструкция для агентов находится в [AGENTS.md](../AGENTS.md).
История поставляемых изменений ведётся в [CHANGELOG.md](../CHANGELOG.md).

Клиенты и backend версионируются независимо. Для каждого выпускаемого клиента
используется собственная версия: Windows, Android, iOS и другие платформы.
В Windows понятие Frontend означает весь установленный клиент: React, Rust/native,
ресурсы, зависимости и упаковку. React и Rust не получают разные продуктовые версии.
Изменение только Windows не повышает версию backend или Android.

## Формат и повышение версии

Продуктовая версия — `MAJOR.MINOR.PATCH`, например `0.2.1`.

| Изменение | Повышение | Пример |
| --- | --- | --- |
| Исправление ошибки, небольшая правка внешнего вида или текста, внутреннее совместимое изменение поставляемого кода/зависимостей | PATCH | `0.2.0 → 0.2.1` |
| Новая возможность, новый экран или существенная совместимая переработка интерфейса | MINOR, PATCH обнуляется | `0.2.1 → 0.3.0` |
| Несовместимый контракт или поведение, требующее перехода пользователей/клиентов | MAJOR, MINOR и PATCH обнуляются | `1.4.2 → 2.0.0` |
| Только документация, тесты, CI или инфраструктура без изменения поставляемого приложения/контракта | Без повышения продуктовой версии | Новый commit/build ID |

После `1.0.0` применяются обычные правила SemVer. До `1.0.0` совместимые
возможности также повышают MINOR, исправления — PATCH; несовместимое изменение
повышает MINOR и явно помечается `BREAKING` в changelog с планом перехода.
Переход на `1.0.0` означает первый согласованный стабильный выпуск; сам номер
не является доказательством готовности VPN, упаковки или эксплуатации.

Версия повышается один раз на завершённую логическую продуктовую задачу, а не
на каждый commit, исправление теста или повторный прогон CI. Следующая
самостоятельная продуктовая задача получает следующую версию, даже если работа
продолжается в том же PR. Внутри задачи выбирается наибольшее необходимое
повышение. Если объём задачи вырос с PATCH до MINOR, целевая версия пересчитывается
от исходной версии задачи. Не повышать версию повторно из-за замечаний к той же задаче.

Уже опубликованные версии и теги не переиспользуются для другого содержимого.
Откат запускает прежний неизменяемый артефакт с его прежней версией; новый
исправленный выпуск получает следующий номер.

## Где хранить версии

| Компонент | Основной источник | Согласованные копии и отображение |
| --- | --- | --- |
| Windows | `apps/windows/package.json:version` | `src-tauri/Cargo.toml:[package].version`, `src-tauri/tauri.conf.json:version`, версия собственного пакета в `src-tauri/Cargo.lock`; UI читает `DesktopAdapter.getVersion()` / Tauri `getVersion()` |
| Backend | `backend/pyproject.toml:[project].version` | Локальный default `Settings.application_version` в `backend/src/prettylisavpn/config.py`, примеры окружения и release metadata; запущенный сервер сообщает фактический `APPLICATION_VERSION` через `GET /version` |
| Другие клиенты | Манифест пакета конкретной платформы, когда клиент вводится в работу | В той же задаче документировать путь, UI-источник и платформенный build number; до этого не присваивать версии заготовкам |

При повышении версии Windows все четыре места проверяются в одной задаче.
Lock-файлы обновляются штатным инструментом, если затронуты их данные; не заменять
версии сторонних зависимостей и не выполнять постороннее обновление зависимостей.
Для backend базовая версия пакета и локальные defaults согласуются в той же
задаче; реальные секретные env-файлы не редактируются в рамках обычного bump.

Таблица задаёт один основной источник на компонент. Согласованные копии пока
поддерживаются явно; автоматическая генерация и проверки их совпадения в CI
ещё не реализованы. Каждый агент обязан сверить значения до сборки и указать
результат в PR. Если будет добавлен автоматический bump/check, его команды
сначала нужно документировать и проверить.

## Версия продукта и идентификатор сборки

Версия описывает изменение продукта. Для точного различения сборок дополнительно
фиксируются компонент, канал, полный SHA реально собранного commit, CI run ID
и attempt. Например, тестовый архив:
`windows-0.2.0-preview-run-123-attempt-1-gabcdef123456.zip`.
Короткий SHA допустим в имени файла; полный SHA обязателен в README/метаданных
артефакта и записи о проверке.

Каналы: `development` для разработки, `preview` для проверки владельцем,
`release` для опубликованного выпуска. Номер CI не является PATCH.
Пересборка того же исходного кода сохраняет продуктовую версию, но получает
собственный run/attempt. В имени Windows-пакета остаётся обычный
`MAJOR.MINOR.PATCH`; канал и идентичность сборки записываются рядом с артефактом.
Текущий интерфейс показывает продуктовую версию; отдельный экран build metadata
ещё не реализован.

В PR `github.sha` может быть временным merge commit. В записи о проверке
различать SHA исходной ветки и SHA, фактически выбранный checkout/сборкой.
Не выдавать результат другого commit или предыдущей сборки за проверку текущего.
Изменение только документации после успешной проверки не требует пересборки
приложения; явно указать проверенный product commit и отдельный docs commit.

Для backend целевой формат runtime-идентификатора:

- локальная разработка без CI: `0.1.1` либо `0.1.1-dev.0+g<полный-SHA>`;
- development/preview сборка: `0.1.1-dev.<run>+g<полный-SHA>`;
- опубликованный выпуск: `0.1.1+g<полный-SHA>`.

Здесь `0.1.1` — базовая версия из pyproject; суффиксы относятся к строке
`APPLICATION_VERSION`, а не к Python package version. Docker-образ фиксируется
digest или уникальным неизменяемым тегом: символ `+` из SemVer нельзя буквально
переносить в Docker tag. В release-записи хранить соответствие версии, SHA и digest.
Build metadata после `+` не влияет на порядок версий SemVer.

Это целевой формат. Сейчас `.github/workflows/backend.yaml` устанавливает
`APPLICATION_VERSION=dev-<полный-SHA>`, а часть инструкций ручного деплоя
использует SHA без SemVer. Эти действующие форматы сохраняются до отдельной задачи
перехода backend CI/deploy/rollback и их проверок. Не переписывать старую историю
и не заявлять, что новый формат уже развёрнут. Клиент показывает полученную
строку версии без попытки сравнить её как SemVer.

## Что означает версия backend в клиенте

Источник — ответ существующего `GET /version`:
`application_name`, `application_version`, `environment`.
Показывается версия сервера, к которому фактически подключён клиент,
а не версия из checkout, локального backend-манифеста или предыдущего скриншота.
При ошибке/пустом значении показывать «недоступна», при ожидании — «…»;
не подставлять номер frontend и не блокировать вход/навигацию.

Совпадение номеров клиента и backend не требуется и не доказывает совместимость.
Версия релиза backend также не является версией HTTP API. В рамках текущего
контракта сохранять совместимость; для BREAKING-задачи сначала зафиксировать
затронутые поля, ошибки, auth/VPN-поведение и поддерживаемые версии клиентов,
порядок миграции и отката. Не добавлять `/v2`, принудительное обновление клиента
или проверку «минимальной версии» без отдельной продуктовой задачи.

Отложенная проверка: подтвердить доступность `/version` на реальном окружении
и соответствие ответа реально запущенному образу; при внедрении целевого
runtime-формата проверять точное значение после deploy и rollback. UI fixtures
и тестовая сборка не подтверждают production-интеграцию.

## Как вносить дальнейшие изменения

1. Прочитать `AGENTS.md`, этот документ, актуальный handoff и относящиеся к задаче
   инструкции. Проверить remote HEAD, состояние PR и незавершённые правки.
   Для новой задачи от актуального develop использовать отдельную рабочую ветку;
   согласованное продолжение текущего открытого PR выполнять в его ветке.
2. Кратко назвать область задачи, затронутые компоненты, исходную и целевую версии
   и причину повышения либо `version unchanged`. Разрешённую задачу выполнять
   без повторного запроса на обычные правки, проверки, commit и push.
3. Реализовать согласованный объём, обновить версии затронутых компонентов,
   добавить запись в `CHANGELOG.md` и обновить документацию/handoff.
   Зависимости от будущего backend описать конкретным контрактом, не подменяя
   интеграцию демонстрационными данными.
4. Выполнить соответствующие lint/typecheck/tests/format и сборку. Для Windows UI
   получить реальные native-скриншоты изменённых экранов и проверить переполнение,
   навигацию и оконные действия. После ошибки исправить её и повторить нужные
   проверки; старый успешный run не закрывает новую непроверенную правку.
   Для изменений только документации достаточно проверить ссылки, согласованность
   правил и diff; не запускать нативную сборку только из-за текста.
   До объявления готовности выполнить [полную проверку CI](ci-verification.md):
   все события и workflow последнего remote HEAD должны завершиться корректно,
   включая запуски после последнего docs/handoff push.
5. Проверить diff, отсутствие секретов и посторонних изменений. Зафиксировать
   commit и отправить ветку в origin, если владелец не запретил. Обновить описание
   PR по итоговому поведению: версии, совместимость, реальные результаты проверок,
   SHA, ссылки на сборку/скриншоты и оставшиеся ограничения.
6. Обновить handoff: запрос, область, версии до/после, проверенный SHA/run,
   будущая работа backend и точка продолжения. Сообщить владельцу результат,
   версии и существенные ограничения. Не называть commit, push, merge, публикацию
   артефакта и production deploy одним действием.

Commit/push обычной разрешённой задачи выполняются автоматически по правилам
репозитория. Merge, создание release-тега/GitHub Release и production deploy
выполняются только в пределах явно поставленной задачи на соответствующее действие.
Существующий автоматический development-deploy при merge в develop учитывать
до слияния; документация сама по себе не меняет настройки этой автоматизации.

## История изменений и выпуск

Для каждой продуктовой задачи добавлять запись в `CHANGELOG.md`: компонент,
целевая версия, Added/Changed/Fixed/Breaking, пользовательский результат и
совместимость. До опубликования запись находится под `Unreleased`, даже если
версия уже обновлена в манифестах. Документация/CI могут иметь собственную
запись без повышения версии приложения.

При задаче на выпуск перенести соответствующие записи под компонент, точную
версию и дату UTC, указать проверенный commit и артефакт/digest. Теги по компонентам:
`windows/v0.2.0`, `backend/v0.1.1`; для других платформ — такой же принцип.
Тег указывает на исходники этого выпуска, не перемещается и не создаётся просто
ради завершения обычной UI-задачи. Общий `v0.2.0` для всего monorepo не используется.

## Принятие правил — 2026-10-16

При принятии правил Windows package.json/Cargo.toml/tauri.conf.json и backend
pyproject объявляют `0.1.0`. Это состояние исходников; оно не подтверждает
существование стабильного релиза или фактическую версию развёрнутого backend.

В PR #1 накоплены изменения Windows: рамка, Rubik, навигация и настройки.
Их переходная версия 0.2.0 применена при следующей задаче полировки UI:
package.json, Cargo.toml, tauri.conf.json и собственная запись Cargo.lock согласованы.
Новый native build проверяется отдельно и фиксируется в handoff; старые exe 0.1.0
не переименовываются. Backend в исходниках остаётся 0.1.0.

Следующую самостоятельную продуктовую Windows-задачу версионировать от 0.2.0.
Backend повышает собственную версию только при своей продуктовой задаче;
переход его runtime-идентификатора и автоматизация согласованности версий
остаются отдельными задачами.
