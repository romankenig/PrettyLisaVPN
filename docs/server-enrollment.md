# Добавление VPN-сервера на любом хостинге

Инструкция для текущего fleet backend и Chrome Extension. Хостинг VPS может быть
Netcup, DigitalOcean, Timeweb или другим: текущие инструменты установки требуют
Ubuntu 24.04+ с systemd, публичный IPv4 и SSH-доступ. Порядок ниже не создаёт и не
оплачивает VPS. Историческая настройка DigitalOcean описана
[отдельно](digitalocean-vpn-node-baseline.md).

## 1. Разделяйте VPS, DNS и сертификат

| Что настраивается | Кто управляет | Необходимый доступ |
| --- | --- | --- |
| Linux, VPN-ядро, прокси, firewall | Владелец VPS на выбранном хостинге | SSH/sudo и, при наличии внешнего firewall, доступ к нему |
| `proxy-…prettylisavpn.com → IPv4` | Авторитетный DNS-сервис домена `prettylisavpn.com` | API-токен DNS или доступ к панели DNS |
| Публичный TLS-сертификат прокси | Certbot на выходном сервере | Корректный DNS, входящий TCP/80 для HTTP-01 и исходящий HTTPS |
| Выдача и отзыв доступа | Backend и fleet worker PrettyLisaVPN | Действующий закрытый fleet admin API |

На 2026-11-05 у `prettylisavpn.com` авторитетные NS — `ns1.timeweb.ru`,
`ns2.timeweb.ru`, `ns3.timeweb.org`, `ns4.timeweb.org`. Это DNS Timeweb независимо
от того, что DE размещён у Netcup, а US — у DigitalOcean. Проверять актуального
DNS-провайдера нужно по NS, а не по имени VPS или его IP:

```sh
dig +short NS prettylisavpn.com @1.1.1.1
```

Добавить запись командами Linux можно через авторизованный API DNS-сервиса.
Одного root-доступа к VPN-серверу недостаточно: `/etc/hosts`, `hostnamectl`,
локальный DNS-сервер и настройка PTR не меняют публичную A-запись домена.
Переносить DNS-зону или менять NS при добавлении каждого VPS не требуется.

API-токен DNS хранить на контроллере установки в секретном хранилище/файле с
ограниченным доступом, отдельно от SSH-ключей и fleet admin token. Не отправлять
его в чат, не коммитить, не выводить в журнал и не копировать на каждый VPN-узел.
Если провайдер позволяет ограничить токен нужной зоной и DNS-операциями,
использовать эти ограничения.

## 2. Зарегистрируйте узел и сохраните его идентичность

1. Запишите имя, страну, публичный IPv4, `expected_egress_ips`, capacity и группу
   доступа. `FREE` доступен Free/Premium/Platinum; правила Premium/Platinum и
   `INTERMEDIATE` сохраняются. Промежуточный RU-узел не является прямым Chrome exit.
2. Получите и проверьте fingerprint SSH host key через доверенный канал провайдера.
   Добавьте ключ в pinned `known_hosts`; не отключайте StrictHostKeyChecking.
3. Добавьте credential alias в закрытый inventory worker: точные host/user/port,
   абсолютные пути к SSH-ключу и `known_hosts`. Приватный ключ не входит в API-запрос.
4. Через `POST /admin/nodes` зарегистрируйте метаданные. Повторный запуск сначала
   сверяет существующий узел по inventory; не создавайте дубликаты.
5. Настройте WireGuard/managed через текущий fleet API, используя непересекающуюся
   адресную сеть. Дождитесь результата операции и реальной проверки узла.

Контракты, блокировки операций, мониторинг и ограничения повторных запросов —
в [fleet lifecycle](fleet-lifecycle.md). Регистрация метаданных сама по себе не
устанавливает ПО и не доказывает работу VPN.

## 3. Создайте DNS для Chrome через API

Каждому выходному серверу назначается постоянное уникальное имя вида
`proxy-<идентификатор>.prettylisavpn.com`. Для нескольких серверов в одной стране
используйте, например, `proxy-de-002.prettylisavpn.com`; одно имя страны нельзя
перенаправлять между серверами с активными сессиями.

Требуемые значения для существующих выходов:

| Сервер | DNS-имя | A-запись |
| --- | --- | --- |
| NL / Timeweb | `proxy-nl.prettylisavpn.com` | `81.31.245.143` |
| DE / Netcup | `proxy-de.prettylisavpn.com` | `5.181.49.183` |
| US / DigitalOcean | `proxy-us.prettylisavpn.com` | `204.48.17.50` |

Алгоритм для контроллера установки, независимо от хостинга VPS:

1. Определить DNS-провайдера и аккаунт, владеющий зоной. NS Timeweb не доказывают,
   что зона доступна именно через API Timeweb Cloud: сначала подтвердить её
   наличие в авторизованном аккаунте. Timeweb Hosting и Cloud могут требовать
   разных API/учётных данных.
2. Прочитать записи **конкретного** имени через API этого DNS-провайдера.
3. Если единственная A-запись уже совпадает с IPv4 узла — ничего не менять.
   Если записи нет — создать её. При конфликте IP, CNAME или AAAA остановить
   настройку этого узла и проверить конфликт; не переписывать всю зону.
4. При неопределённом ответе записи сначала перечитать состояние: не повторять
   создание вслепую. Использовать постоянный идентификатор запроса, если API
   поддерживает идемпотентность.
5. Использовать обычную DNS-запись без CDN/HTTP-проксирования. Chrome 0.1.0
   подключается к HTTPS-прокси на динамическом TCP-порту `40000–49899`.
   AAAA пока не публиковать: этот транспорт обслуживает IPv4.
6. Сверить ответ авторитетных NS и публичных резолверов. Переходить к TLS только
   после того, как имя разрешается ровно в ожидаемый адрес.

Пример **контракта**, если зона действительно принадлежит аккаунту Timeweb Cloud:
`POST https://api.timeweb.cloud/api/v1/domains/prettylisavpn.com/dns-records`,
авторизация Bearer и JSON:

```json
{
  "type": "A",
  "subdomain": "proxy-de.prettylisavpn.com",
  "value": "5.181.49.183",
  "ttl": 300
}
```

Это пример по [официальному API](https://github.com/timeweb-cloud/sdk-javascript/blob/main/docs/DomainsApi.md#createdomaindnsrecord)
и [схеме запроса](https://github.com/timeweb-cloud/sdk-javascript/blob/main/docs/CreateDns.md),
а не проверенная интеграция с аккаунтом владельца. Без DNS-доступа запрос не
выполнять; готового DNS-adapter в репозитории пока нет. Ни fleet registration,
ни сертификатный playbook сами A-записи не создают. После подключения API-доступа
этот шаг может выполняться контроллером автоматически, без посещения панели VPS.

Команды чтения DNS выполняются на Linux-контроллере или сервере:

```sh
proxy_name=proxy-de.prettylisavpn.com
dig +short A "$proxy_name" @ns1.timeweb.ru
dig +short A "$proxy_name" @1.1.1.1
dig +short A "$proxy_name" @8.8.8.8
dig +short AAAA "$proxy_name" @1.1.1.1
```

Если NS сменились, в первой команде использовать фактический авторитетный сервер.
Пустой/старый ответ не считается успехом; кеширование и отрицательные DNS-ответы
могут задержать видимость новой записи.

## 4. Выпустите сертификат существующим playbook

Проверить входящий TCP/80 для ACME и возможность клиентского доступа к выделяемым
TCP-портам `40000–49899` одновременно во внешнем firewall хостинга и на узле.
Существующие правила SSH, WireGuard, managed transports и firewall deadlines
сохранить. Если порт 80 занят, сначала согласовать способ HTTP-01; не останавливать
чужой веб-сервис автоматически. HTTPS-соединения прокси не используют CDN.

На Linux-контроллере из корня проверенного checkout:

```sh
ansible-playbook \
  --inventory /secure/path/ansible-inventory.yml \
  --limit new_exit \
  infra/ansible/browser-proxy-certificate.yml \
  --extra-vars 'proxy_host=proxy-de.prettylisavpn.com'
```

`new_exit` — alias в **Ansible** inventory с публичным IPv4 в `ansible_host`,
SSH-пользователем, ключом и pinned `known_hosts`. Файл alias-учётных данных worker
имеет другую схему и не является готовым Ansible inventory. Playbook должен
выполняться только для выбранного узла.

Playbook проверяет имя/DNS, устанавливает Certbot, получает публичный сертификат
и включает `certbot.timer`. Приватный TLS-ключ остаётся на узле. На самом узле:

```sh
sudo systemctl is-enabled certbot.timer
sudo systemctl is-active certbot.timer
sudo openssl x509 \
  -in /etc/letsencrypt/live/proxy-de.prettylisavpn.com/fullchain.pem \
  -noout -subject -issuer -dates
sudo certbot renew --cert-name proxy-de.prettylisavpn.com --dry-run
```

Подставить имя выбранного узла. HTTP-01 должен оставаться доступным для продления;
внешний firewall также не должен его блокировать.

## 5. Включите возможность Chrome на готовом узле

Через `POST /admin/nodes/{id}/methods/managed/configuration` передайте **текущие**
`server_name` и `reality_target` этого узла плюс его `proxy_host`. Не заменяйте
native-параметры значениями другого сервера. Используйте UUID `Idempotency-Key`
и опрашивайте `GET /admin/operations/{id}` до завершения.

Bootstrap установит актуальные `node.py`, `managed.py` и `browser_proxy.py` из
развёрнутого backend. Имеющиеся node-owned ключи и активные native leases должны
сохраниться. Менять proxy_host с активными proxy leases запрещено. При FAILED
сохранить код ошибки, устранить причину; новую попытку выполнять отдельной
операцией после подтверждённого завершения предыдущей.

Новый узел должен пройти штатную проверку и иметь состояние READY. Chrome
показывает только узлы с настроенным proxy_host и учитывает группу/доступность.
Наличие DNS и сертификата само по себе не делает сервер доступным в приложении.

## 6. Примите новый выход по реальному трафику

В отдельном профиле Chrome и с тестовой учётной записью проверить: реальный OTP,
список стран, выделение сессии, статус Connected после проверки выхода, внешний
IP выбранного узла, HTTP/HTTPS/WSS, удалённый DNS, запрет IPv6/private targets,
отключение, переподключение, смену сети, heartbeat expiry, отзыв устройства и
возврат неиспользованного Free-времени после подтверждённой очистки.

Проверить прямое подключение из клиентской сети. SSH-проброс, работа API,
fixture-скриншоты или успешный тест из другого VPS — отдельные доказательства,
которые не заменяют эту проверку. Не переключать личный VPN пользователя без
его поручения. По завершении закрыть все тестовые leases и отозвать временные
доступы; сохранить только обезличенные результаты, SHA/run/attempt и версии.
