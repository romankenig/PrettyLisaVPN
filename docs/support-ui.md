# О приложении и поддержка — Windows 0.9.0 / backend 0.4.0

About показывает frontend/backend из существующего useVersions. Номер backend
получается только через GET /version, при недоступности — «недоступна».
Окружение и eyebrow удалены. FAQ пока содержит только заголовок, без выдуманных
ответов. Внизу полупрозрачная строка `inspired by love of my life, Lisa`.

## Форма

«Написать в поддержку» открывает modal dialog поверх приложения: тема до 120,
описание до 4000, email для ответа до 254 символов. Email предзаполнен из профиля,
его можно изменить. Поля сохраняют обычный цвет и регистр вводимых данных.
Escape, крестик и отмена закрывают форму, возвращая фокус; черновик и файлы не
сохраняются на диск/localStorage и удаляются при закрытии/смене аккаунта.

Скриншоты выбирает пользователь, автоматического захвата экрана нет. До 3 файлов,
PNG/JPEG/WebP, до 5 MiB каждый и 10 MiB в сумме. До добавления проверяются MIME,
сигнатура и размеры. Некорректная новая пачка не удаляет ранее выбранные файлы.
Файл можно убрать. Эти проверки не заменяют серверную проверку содержимого.

## Технические данные

Отдельный checkbox «приложить технические данные» включён по умолчанию, его
можно отключить. «Что будет приложено» показывает точный JSON whitelist:

- schema_version и collected_at в UTC;
- фактические frontend/backend версии, недоступная версия — null;
- platform=WINDOWS, язык и часовой пояс;
- тариф и непрозрачный ID текущей auth-сессии для поиска серверного события;
- текущие phase/backend/tunnel VPN, ID VPN-сессии и нормализованный failure_code,
  если они известны. История прошлых сессий не собирается.

Нет access/refresh tokens, OTP, ключей, адресов посещений, DNS-запросов, IP/города,
публичных endpoint, конфигурации туннеля, системных логов, имени компьютера,
списка процессов и истории трафика. Проекция создаётся по полям, без сериализации
сырой session/config. ID сессий не являются токенами; они видны в предпросмотре.
Email отправляется только как явно выбранный адрес ответа, не дублируется в
диагностике. Пользовательские описание и скриншоты не подвергаются автоматической
редакции; это явно выбранные вложения, не фоновый сбор данных.

## Приём и статус

Production ApplicationState подключает HTTP SupportSender через общий native
transport. SMTP-пароль и адресат не попадают в Windows bundle.

- POST /support/requests: Bearer, multipart/form-data. Одна текстовая часть
  `report` — JSON с request_id (UUID), subject, description, reply_email,
  diagnostics (whitelist либо null). Части screenshots повторяются до трёх раз.
- 202 `{ "request_id": "...", "status": "ACCEPTED" }` — commit обращения,
  очищенных вложений и состояния очереди в PostgreSQL. Повтор возвращает
  текущее состояние того же обращения.
- GET /support/requests/{request_id}: Bearer, 200 с теми же двумя полями.
  Статус принадлежит аккаунту, доступен с другого его устройства. Чужое и
  несуществующее обращение возвращают одинаковый 404 SUPPORT_NOT_FOUND.
- ACCEPTED: сохранено/ожидает SMTP; RETRYING: ожидает повтора; SENT: SMTP принял
  письмо; FAILED: восемь попыток исчерпаны, обращение сохранено; EXPIRED:
  содержимое удалено по сроку хранения. SENT не доказывает доставку во входящие.
- Ошибки `{error:{code}}`: AUTH_INVALID (401), INVALID_REQUEST (422),
  ATTACHMENT_REJECTED (422/413), RATE_LIMITED (429), IDEMPOTENCY_CONFLICT (409),
  SUPPORT_UNAVAILABLE (503). Приватные ответы: no-store и Vary: Authorization.

Идемпотентность привязана к (account_id, request_id); fingerprint включает полный
report и исходные байты/типы вложений. Иной payload с тем же ключом — 409.
Конкурентные запросы и квота сериализуются в БД по аккаунту. Не более пяти новых
обращений в час и двадцати в сутки. Повтор проходит и при исчерпанной квоте.

Windows сохраняет UUID и полный снимок попытки, включая collected_at, в памяти
открытой формы. Повтор неизменённого черновика использует этот же снимок.
Sender сначала запрашивает статус; только подтверждённый 404 разрешает POST с
исходным UUID. Ошибка проверки статуса не считается отсутствием обращения.
После потери ответа на уже принятый POST повтор находит существующее обращение.
Явное редактирование формы начинает новое обращение с новым UUID.

Закрытие/смена аккаунта удаляет память формы и прерывает ожидание, но не отменяет
уже принятый сервером запрос. UUID/черновик не сохраняются на диск.
Popup показывает номер и подтверждённый статус; «проверить статус» обновляет его.
Ошибка оставляет черновик и не выводит сырой текст сервера.

## Проверка и хранение

Report и все вложенные объекты запрещают неизвестные поля. Версии, коды VPN,
локаль, часовой пояс и тариф ограничены схемой. Время диагностики — UTC.
Auth/VPN session IDs проверяются на принадлежность аккаунту; неподтверждённые
удаляются из диагностики. Клиентские состояния/версии — пользовательские данные,
их нельзя считать доверенной серверной телеметрией.

До multipart parsing body ограничен 10 MiB + 64 KiB для framing/JSON. Reverse
proxy дополнительно ограничивает его 11 MB. Report — до 32 KiB. Одновременно обрабатывается один upload на процесс (tmpfs контейнера 16 MiB);
приём/декодирование ограничены timeout 30 секунд. PNG/JPEG/WebP
действительно декодируются: до 12 млн пикселей, до 8192 на сторону, без анимации.
Затем сервер заново формирует PNG из пикселей, без EXIF, ICC и текстовых chunks.
Имена задаёт сервер; оригиналы не сохраняются. После очистки снова действуют
5 MiB на файл и 10 MiB суммарно. HTML/SVG и другие форматы запрещены.

PostgreSQL хранит обращение, BYTEA-вложения и очередь одной транзакцией.
Локальные файлы контейнера и Redis не нужны для сохранности. API выдаёт только
статус, без текста/email/диагностики/вложений. Payload, файлы, email, parser/SMTP
exceptions и секреты не логируются. Доступ к БД/backup — административный;
наличие шифрования дисков/backup из этой реализации не следует.

Worker удаляет payload/вложения через 30 суток, включая неотправленные. Минимальная
запись (account, UUID, fingerprint, status, timestamps, attempts) остаётся до удаления
аккаунта для защиты от поздних повторов; статус EXPIRED. Удаление аккаунта каскадно
удаляет и обращения. Это логическое удаление из рабочей БД; backup retention и
срок хранения писем в сервисном ящике управляются отдельно оператором.

## Письмо и очередь

From/envelope sender: app-helper@prettylisavpn.com. To/envelope recipient:
help@prettylisavpn.com зафиксирован на сервере. Reply-To — проверенный reply_email.
Тема не допускает управляющих символов; письмо plain text с очищенными PNG.
SMTP использует общие Timeweb host/port/TLS/timeouts, отдельный username и
SUPPORT_SMTP_PASSWORD. Development берёт пароль из DEV_SUPPORT_SMTP_PASSWORD;
пароль auth не переиспользуется. Deployment требует отдельный secret.
Без SMTP-пароля сервер может устойчиво принимать обращения, очередь ожидает
настройки, SENT не выставляется.

FOR UPDATE SKIP LOCKED исключает одновременную отправку одной строки разными
workers. До восьми попыток с паузами 30, 60, 120… секунд, предел один час;
перезапуск продолжает очередь из БД. После восьми ошибок — FAILED.
Message-ID стабилен. При сбое между SMTP DATA и commit SENT письмо может
повториться с тем же Message-ID: SMTP не даёт exactly-once. Второе обращение в
БД при этом не создаётся.

## Поставка и доказательства

Backend 0.4.0, additive migration 0020_support_requests; application rollback
оставляет таблицы и обращения. Windows 0.9.0 подключает sender/status. Другим
платформам требуется собственный адаптер общего HTTP-контракта.

Unit/integration проверки: приватная схема, изображения, владение, повторы,
конкуренция, квоты, сбой SMTP/рестарт, retention. Native Windows review собирает
текущий исходник и снимает форму, потерю ответа, повтор и статус на синтетическом
loopback API; настоящую почту этот сценарий не отправляет.
Точные CI, product/build SHA, native artifacts, development deploy и реальная
SMTP-проверка фиксируются в task PR. Скриншот не является доказательством inbox delivery.
