# О приложении и поддержка — Windows 0.7.0

About показывает frontend/backend из существующего useVersions. Номер backend
получается только через GET /version, при недоступности — «недоступна».
Окружение и eyebrow удалены. FAQ пока содержит только заголовок, без выдуманных
ответов. Внизу полупрозрачная строка `inspired by love of my life, Lisa`.

## Форма

«Написать в поддержку» открывает modal dialog поверх приложения: тема до 120,
описание до 4000, email для ответа до 254 символов. Email предзаполнен из профиля,
его можно изменить. Поля сохраняют обычный цвет и регистр вводимых данных.
Escape, крестик и отмена закрывают форму, возвращая фокус; черновик и файлы не
сохраняются на диск/localStorage и удаляются при закрытии/смене аккаунта.

Скриншоты выбирает пользователь, автоматического захвата экрана нет. До 3 файлов,
PNG/JPEG/WebP, до 5 MiB каждый и 10 MiB в сумме. До добавления проверяются MIME,
сигнатура и размеры. Некорректная новая пачка не удаляет ранее выбранные файлы.
Файл можно убрать. Эти проверки не заменяют серверную проверку содержимого.

## Технические данные

Отдельный checkbox «приложить технические данные» включён по умолчанию, его
можно отключить. «Что будет приложено» показывает точный JSON whitelist:

- schema_version и collected_at в UTC;
- фактические frontend/backend версии, недоступная версия — null;
- platform=WINDOWS, язык и часовой пояс;
- тариф и непрозрачный ID текущей auth-сессии для поиска серверного события;
- текущие phase/backend/tunnel VPN, ID VPN-сессии и нормализованный failure_code,
  если они известны. История прошлых сессий не собирается.

Нет access/refresh tokens, OTP, ключей, адресов посещений, DNS-запросов, IP/города,
публичных endpoint, конфигурации туннеля, системных логов, имени компьютера,
списка процессов и истории трафика. Проекция создаётся по полям, без сериализации
сырой session/config. ID сессий не являются токенами; они видны в предпросмотре.
Email отправляется только как явно выбранный адрес ответа, не дублируется в
диагностике. Пользовательские описание и скриншоты не подвергаются автоматической
редакции; это явно выбранные вложения, не фоновый сбор данных.

## Текущее состояние и будущая отправка

SupportSender — отдельный необязательный порт ApplicationState. В production и
native review он не задан: кнопка «отправить» отключена, видно «отправка пока
недоступна». Писем/HTTP запросов нет. Ни mailto, ни SMTP из приложения не используются.
Адрес получателя ещё не выбран и будет конфигурацией backend, не VITE/клиента.

Подключённый в будущем sender получает SupportSubmission, access token отдельно
от пользовательского payload и AbortSignal. Двойное нажатие блокируется, закрытие
прерывает ожидание. Успех показывается лишь после подтверждённого request_id,
формулировка «обращение принято» не обещает доставку письма в ящик. Ошибка не
очищает черновик и не показывает сырой текст сервера.

Предлагаемый HTTP-контракт для отдельной задачи backend/frontend:

- POST /support/requests, авторизация Bearer, multipart/form-data.
- `report`: JSON с request_id (UUID), subject, description, reply_email,
  diagnostics (объект whitelist либо null).
- Повторяемая часть `screenshots`: только выбранные файлы, безопасные имена.
- 202 `{ "request_id": "...", "status": "ACCEPTED" }` означает, что обращение
  надёжно записано/поставлено в очередь. Это ещё не подтверждение email delivery.
- Стабильные ошибки: SUPPORT_UNAVAILABLE, INVALID_REQUEST, ATTACHMENT_REJECTED,
  RATE_LIMITED, AUTH_INVALID. Backend сам находит владельца по токену.

До подключения реального sender нужны: HTTP/upload-адаптер с timeout, проверкой
ответа и MIME; устойчивый ключ на повтор после timeout, серверная идемпотентность
и получение статуса по request_id, чтобы не плодить обращения при неопределённом
результате. Текущий UI создаёт UUID на попытку и не является готовым механизмом
надёжных повторов. Отмена окна не должна обещать отмену уже принятого обращения.

Backend должен проверить длины, количество/размер/настоящее содержимое изображений,
ограничить декодированные размеры, убрать EXIF и прочие необязательные метаданные,
не доверять имени/MIME клиента. Не поддерживать HTML/SVG/исполняемые вложения.
Проверить принадлежность session IDs аккаунту либо проигнорировать неподтверждённые.
Защитить email headers от инъекции; From — серверный сервисный адрес, Reply-To —
проверенный reply_email. Адресата нельзя выбирать произвольным полем клиента.

Нужны очередь доставки/повторы провайдера, безопасное хранение и срок удаления
обращений/вложений, ограничение частоты и размера, тесты ошибок и контроль доступа.
Не логировать payload, текст обращения, email, содержимое файлов и секреты.
Серверная поддержка и frontend sender пока не реализованы; source backend 0.1.0
не меняется. Unit fake проверяет UI, native review использует синтетические
профиль/сессии/скриншоты; доставка настоящего письма не проверялась.
