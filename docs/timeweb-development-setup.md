# Тестовое окружение в Timeweb Cloud

Здесь описана ручная подготовка тестового окружения PrettyLisaVPN: один Ubuntu VPS для Backend и две управляемые базы — PostgreSQL и Valkey. Действия выполняются в панели Timeweb и через SSH. Сам документ не создаёт облачные ресурсы.

Все три ресурса размещайте в одном проекте, регионе и приватной BGP-сети. Приватная сеть обеспечивает связь VPS с базами без публикации их портов в интернете. Прикрепление сети в панели ещё не гарантирует настройку адреса внутри Ubuntu: это нужно проверить отдельно по инструкции провайдера.

```text
Компьютер администратора
        │ SSH, TCP 22 только с доверенного IP
        ▼
VPS Ubuntu: публичный IP + приватный IP
        │                           │
        ▼                           ▼
Управляемый PostgreSQL       Управляемый Valkey
только приватный адрес      только приватный адрес
```

Backend в этом варианте доступен на `127.0.0.1:8000` самого VPS. Порт 8000 не открывается в интернет. Для публичного HTTPS используйте [развёртывание с Caddy](backend-deployment.md), а не публичную публикацию Uvicorn. VPN-узлы в это окружение не входят; пользовательский VPN-трафик через данный VPS не проходит.

## 1. Подготовьте параметры и бюджет

Ниже — исходный профиль небольшого тестового окружения, а не гарантия производительности или доступности конкретного тарифа. Перед заказом проверьте фактические версии, ресурсы и стоимость в панели. После нагрузочных проверок пересмотрите размеры по CPU, памяти, диску, числу соединений и задержкам.

| Ресурс | Исходный профиль | Для чего |
| --- | --- | --- |
| VPS | Ubuntu 24.04 LTS, 2 vCPU, 4 ГБ RAM, 30 ГБ Premium NVMe, один сервер | Docker, Backend и при необходимости reverse proxy. Для сборки образа также нужны свободные память и диск. |
| PostgreSQL | Версия 17, 1 CPU, 2 ГБ RAM, 20 ГБ диска, один узел, резервные копии | Постоянные данные приложения. Реплики для первоначального тестового окружения не обязательны. |
| Valkey | Версия 8.1, 1 CPU, 1 ГБ RAM, минимальный доступный диск, один узел | Временные данные; не является источником истины. |

Изменение размера и версии управляемой базы может иметь ограничения. Проверьте их до заказа, особенно возможность уменьшения тарифа, резервное копирование и автоматическое расширение диска. Не включайте платное автоматическое масштабирование без понятного лимита бюджета.

Подготовьте таблицу значений в своей системе учёта. Пароли храните отдельно в менеджере секретов; не вставляйте их в эту инструкцию или Git.

| Обозначение | Откуда взять |
| --- | --- |
| `TIMEWEB_PROJECT`, `TIMEWEB_REGION` | Выбранные проект и регион для всех ресурсов. |
| `PRIVATE_NETWORK_NAME`, `PRIVATE_CIDR` | Имя и диапазон приватной сети из панели. CIDR — запись диапазона, например `10.20.0.0/24`. |
| `VPS_PUBLIC_IP`, `VPS_PRIVATE_IP` | Публичный и приватный адреса VPS. |
| `SSH_USER`, `LOCAL_PRIVATE_KEY_PATH` | Пользователь из команды SSH провайдера и путь к приватному ключу на вашем компьютере. |
| `ADMIN_PUBLIC_CIDR` | Ваш доверенный внешний адрес, обычно с `/32` для одного IPv4. |
| `POSTGRES_PRIVATE_HOST`, `POSTGRES_PORT` | Приватный адрес и фактический порт PostgreSQL. |
| `POSTGRES_DATABASE`, `POSTGRES_USER` | Название базы и пользователь PostgreSQL. |
| `VALKEY_PRIVATE_HOST`, `VALKEY_PORT`, `VALKEY_USER` | Адрес, порт и пользователь Valkey из панели подключения. |
| Пароли и параметры TLS | Страница подключения каждой базы; пароли являются секретами. |
| `REPOSITORY_URL`, `RELEASE_REF` | URL репозитория и проверенный неизменяемый тег/коммит. |

Названия разделов панели могут изменяться. Используйте данные карточки конкретного ресурса, а не предполагаемые адреса и порты из примеров.

## 2. Создайте приватную сеть

1. Войдите в Timeweb Cloud и выберите `TIMEWEB_PROJECT`.
2. В разделе сетей создайте приватную BGP-сеть в `TIMEWEB_REGION`.
3. Задайте понятное имя `PRIVATE_NETWORK_NAME` и диапазон `PRIVATE_CIDR`, не пересекающийся с уже используемыми сетями.
4. Запишите назначенный диапазон и зарезервированные провайдером адреса. Не назначайте служебные адреса вручную.
5. Подключайте VPS и обе базы к этой же сети. Если ресурс уже существует, проверьте возможность присоединения через страницу сети.

При подключении сервера выполните показанные Timeweb действия внутри Ubuntu. Это существенно: без корректного приватного IP и маршрута Backend не сможет обратиться к базе даже при правильном пароле. См. [добавление сервисов в BGP-сеть](https://timeweb.cloud/docs/vpc/managing-bgp-networks/adding-services-to-bgp).

## 3. Создайте Ubuntu VPS

1. Откройте создание облачного сервера и выберите обычный образ Ubuntu 24.04 LTS, а не готовое приложение из маркетплейса.
2. Укажите общий регион и согласованный профиль ресурсов из шага 1.
3. Назначьте публичный IPv4 для SSH, подключите приватную сеть и запишите оба адреса.
4. В настройках авторизации загрузите **публичный** SSH-ключ администратора. Приватный ключ остаётся на его компьютере.
5. Укажите проект и понятное имя тестового сервера, проверьте стоимость и создайте ресурс.
6. Скопируйте из карточки точную команду SSH. Имя пользователя зависит от образа и настройки провайдера: не предполагайте, что это обязательно `ubuntu` или `root`.

### Сетевой экран

Создайте и прикрепите к VPS группу правил. Применяйте минимально необходимые разрешения; перед включением убедитесь, что разрешён ваш SSH-адрес.

| Направление | Протокол и порт | Адрес | Назначение |
| --- | --- | --- | --- |
| Входящий | TCP 22 | Только `ADMIN_PUBLIC_CIDR` | Администрирование SSH. |
| Входящий | TCP 443 | Интернет, когда настроен HTTPS | Публичный API; до установки reverse proxy не требуется. |
| Входящий | TCP 80 | Интернет, когда настроен Caddy | Получение сертификата и перенаправление на HTTPS. |
| Входящий | TCP 8000 | Не разрешать | API доступен через loopback или внутреннюю Docker-сеть. |
| Исходящий | TCP 80/443 | Источники пакетов, реестр и необходимые внешние API | Установка, обновления и зависимости; используйте фактические протоколы репозиториев. |
| Исходящий | UDP/TCP 53 | Настроенные DNS-серверы | Разрешение имён. |
| Исходящий | UDP 123 | Серверы времени | Синхронизация часов. |
| Исходящий | TCP `POSTGRES_PORT` | PostgreSQL в приватной сети | Соединение с базой. |
| Исходящий | TCP `VALKEY_PORT` | Valkey в приватной сети | Соединение с временным хранилищем. |

У баз не должно быть публичных входящих правил. Если для базы настраивается отдельный список разрешённых адресов, разрешите порт с `VPS_PRIVATE_IP/32`. В панели проверьте, является ли группа разрешающей или запрещающей, и как обрабатывается остальной трафик. Для HTTP/3 у Caddy дополнительно нужен входящий UDP 443.

### Проверка SSH и приватного адреса

На своём компьютере выполните, заменив заполнители:

```sh
ssh -i LOCAL_PRIVATE_KEY_PATH SSH_USER@VPS_PUBLIC_IP
```

Сверьте отпечаток ключа сервера с доверенными данными панели/консоли. После входа выполните на VPS:

```bash
id
hostnamectl
ip address
ip route
```

Ожидаются нужный пользователь, выбранная Ubuntu, назначенный приватный адрес и маршрут к сети баз. Если SSH недоступен, используйте консоль провайдера для диагностики сетевых правил и службы SSH. Постоянное разрешение SSH со всего интернета не является необходимым исправлением.

### Подготовка программ

Установите Docker Engine и Compose по [шагу 2 инструкции VPS](backend-deployment.md), включая обновления ОС и Git. Используйте один способ установки Docker; не смешивайте пакеты Ubuntu и официального репозитория Docker.

Затем на VPS установите клиенты для проверки баз:

```bash
sudo apt update
sudo apt install -y postgresql-client redis-tools netcat-openbsd
sudo docker version
sudo docker compose version
```

Здесь устанавливаются клиенты, а не серверы баз. Администрируйте Docker через `sudo`, назначьте ответственного за обновления безопасности Ubuntu и периодическую проверку резервных копий.

## 4. Создайте управляемый PostgreSQL

1. В разделе баз данных выберите PostgreSQL 17 и согласованный профиль. Если версия недоступна, сначала согласуйте альтернативу и её проверку с приложением.
2. Разместите один узел в том же регионе и проекте, подключите приватную сеть. Публичные IPv4/IPv6 базе не назначайте.
3. Включите резервное копирование и выберите окно обслуживания, не мешающее работе команды. Зафиксируйте срок хранения и порядок восстановления.
4. Создайте базу и отдельного пользователя с уникальным паролем. Не используйте демонстрационный пароль локального Compose.
5. Проверьте стоимость, создайте кластер и дождитесь готовности.
6. На странице подключения запишите приватный хост, порт, базу, пользователя, TLS и требования к сертификатам. Пароль сохраните в менеджере секретов.

На VPS сначала проверьте сеть:

```bash
nc -vz POSTGRES_PRIVATE_HOST POSTGRES_PORT
```

Успех означает доступность TCP-порта, но ещё не проверяет пароль. Затем проверьте вход и выполнение запроса:

```bash
psql -h POSTGRES_PRIVATE_HOST -p POSTGRES_PORT -U POSTGRES_USER -d POSTGRES_DATABASE -W -c 'SELECT 1;'
```

`-W` запрашивает пароль интерактивно, не помещая его в историю команд. Если провайдер требует TLS или дополнительные параметры, используйте его команду подключения с сохранением этих требований. Успешный результат — одна строка со значением `1`.

Ошибка TCP указывает на адрес, маршрут, приватную сеть или сетевой экран. Ошибка авторизации — на имя базы, пользователя или пароль. Ошибка сертификата — на TLS-настройки; не обходите её отключением защиты.

## 5. Создайте управляемый Valkey

1. Выберите Valkey 8.1 и согласованный профиль из шага 1; проверьте доступность версии в регионе.
2. Создайте один узел в общем проекте и приватной сети, без публичных IPv4/IPv6.
3. На первом этапе оставьте стандартные параметры движка. Valkey предназначен для временных данных, постоянные бизнес-данные принадлежат PostgreSQL.
4. Задайте отдельный уникальный пароль, проверьте цену и создайте ресурс.
5. После готовности сохраните приватный хост, фактический порт, пользователя и TLS-настройки. Даже если в панели указан пользователь `default`, копируйте фактическое значение, а не угадывайте его.

На VPS проверьте TCP:

```bash
nc -vz VALKEY_PRIVATE_HOST VALKEY_PORT
```

Для подключения без TLS:

```bash
redis-cli -h VALKEY_PRIVATE_HOST -p VALKEY_PORT --user VALKEY_USER --askpass PING
```

Если провайдер требует TLS, используйте вместо этого:

```bash
redis-cli --tls -h VALKEY_PRIVATE_HOST -p VALKEY_PORT --user VALKEY_USER --askpass PING
```

Применяйте ровно тот вариант и параметры сертификатов, которые соответствуют кластеру. Ожидаемый ответ — `PONG`. `--askpass` запрашивает пароль интерактивно; `-a PASSWORD` использовать не нужно, поскольку пароль может попасть в историю и список процессов.

## 6. Настройте Backend

Приложение читает готовые `POSTGRES_URL` и `VALKEY_URL`, а не отдельные переменные хоста и пароля. Полный контракт с допустимыми значениями приведён в [настройках Backend](../backend/README.md).

Создайте файл настроек на VPS **один раз**:

```bash
sudo install -d -m 0700 -o root -g root /etc/prettylisavpn
sudo install -m 0600 -o root -g root /dev/null /etc/prettylisavpn/backend.env
sudoedit /etc/prettylisavpn/backend.env
```

Повторный `install` из `/dev/null` очищает файл, поэтому существующие настройки меняйте только через `sudoedit`.

Заполните шаблон своими значениями. Фигурные скобки обозначают заполнители, которые надо заменить вместе со скобками:

```dotenv
APPLICATION_NAME=PrettyLisaVPN
APPLICATION_VERSION={DEPLOYED_APPLICATION_VERSION}
ENVIRONMENT=development
LOG_LEVEL=INFO
POSTGRES_URL=postgresql+asyncpg://{POSTGRES_USER}:{URL_ENCODED_POSTGRES_PASSWORD}@{POSTGRES_PRIVATE_HOST}:{POSTGRES_PORT}/{POSTGRES_DATABASE}
VALKEY_URL=redis://{VALKEY_USER}:{URL_ENCODED_VALKEY_PASSWORD}@{VALKEY_PRIVATE_HOST}:{VALKEY_PORT}/0
DEPENDENCY_TIMEOUT_SECONDS=2
POSTGRES_POOL_SIZE=5
POSTGRES_MAX_OVERFLOW=5
```

Используйте `rediss://`, если Valkey требует TLS, и сохраните нужные PostgreSQL TLS-параметры при замене схемы провайдерского URL на `postgresql+asyncpg://`. Специальные символы реквизитов кодируйте для URL: например, `@` внутри пароля как `%40`. Не отправляйте пароли в онлайн-кодировщики.

Проверьте только владельца и права, не печатая содержимое:

```bash
sudo stat -c '%U %G %a %n' /etc/prettylisavpn/backend.env
```

Ожидается `root root 600`. Не публикуйте вывод окружения, полный `docker inspect` или Compose `config`: они могут раскрывать строки подключения.

## 7. Соберите и запустите тестовый Backend

Этот вариант использует `docker run` и сохраняет `ENVIRONMENT=development`. Не запускайте его одновременно с другим Backend на том же порту 8000. Для Backend + Caddy выберите вместо него [основной сценарий развёртывания](backend-deployment.md).

На VPS получите конкретную проверенную версию:

```bash
sudo install -d -o "$USER" -g "$USER" /opt/prettylisavpn
git clone REPOSITORY_URL /opt/prettylisavpn/source
git -C /opt/prettylisavpn/source checkout --detach RELEASE_REF
cd /opt/prettylisavpn/source
release_commit=$(git rev-parse HEAD)
sudo docker build --pull --tag "prettylisavpn-backend:$release_commit" backend
printf 'Версия для APPLICATION_VERSION: %s\n' "$release_commit"
sudoedit /etc/prettylisavpn/backend.env
```

Хеш коммита делает тег однозначным. Укажите напечатанный хеш в `APPLICATION_VERSION`. Для приватного Git используйте утверждённый доступ, не встраивая токен в URL.

После успешной сборки запустите контейнер в том же SSH-сеансе:

```bash
sudo docker run --detach --name prettylisa-backend --restart unless-stopped --init --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m --cap-drop ALL --security-opt no-new-privileges:true --stop-timeout 30 --publish 127.0.0.1:8000:8000 --env-file /etc/prettylisavpn/backend.env "prettylisavpn-backend:$release_commit"
sudo docker inspect --format '{{.State.Status}} {{.State.Health.Status}}' prettylisa-backend
```

Контейнер работает в фоне, без административных Linux-возможностей, с файловой системой только для чтения и временным `/tmp`. На штатное завершение отводится 30 секунд. При первом просмотре здоровье может быть `starting`; дождитесь `healthy`. Политику перезапуска использует Docker, включённый при старте VPS.

Проверьте на VPS:

```bash
curl --fail --silent --show-error http://127.0.0.1:8000/health
curl --fail --silent --show-error http://127.0.0.1:8000/ready
curl --fail --silent --show-error http://127.0.0.1:8000/version
```

Все методы должны вернуть HTTP 200, а `/version` — нужную версию и `development`. `/health` отвечает 200 даже при отказе базы; `/ready` в таком случае отвечает 503. Для логов используйте `sudo docker logs --tail 100 prettylisa-backend`.

Чтобы открыть API в браузере своего компьютера без публичного порта 8000, в **отдельном локальном терминале** создайте SSH-туннель:

```sh
ssh -N -L 18000:127.0.0.1:8000 SSH_USER@VPS_PUBLIC_IP
```

Пока команда работает, откройте `http://127.0.0.1:18000/ready` на своём компьютере. `-L` пересылает локальный порт через SSH на loopback VPS, `-N` не запускает удалённую команду. `Ctrl+C` закрывает туннель. При необходимости добавьте `-i LOCAL_PRIVATE_KEY_PATH`.

Для последующих изменений используйте [обновление варианта с docker run](vps-maintenance.md#docker-run-update): там приведены сохранение старой версии, обновление Git, сборка, замена контейнера и откат. Обычный `docker restart` новые исходники не применяет.

## Проверка готовности окружения

- [ ] Все ресурсы находятся в согласованном проекте, регионе и приватной сети.
- [ ] Приватный адрес и маршрут VPS проверены внутри Ubuntu.
- [ ] SSH доступен только администраторам, приватный ключ не загружен на VPS или в Git.
- [ ] PostgreSQL и Valkey не имеют публичного доступа; с VPS получены `SELECT 1` и `PONG`.
- [ ] Резервные копии PostgreSQL включены, порядок восстановления и окно обслуживания записаны.
- [ ] Docker запускается автоматически; назначен ответственный за обновления ОС.
- [ ] Env-файл доступен только root; указаны правильные URL, TLS, версия и окружение.
- [ ] Backend привязан к loopback; `/health`, `/ready` и `/version` проверены.
- [ ] Сохранены предыдущий образ и порядок отката для следующего обновления.
- [ ] Записаны владельцы ресурсов, бюджет и дата пересмотра/удаления тестового окружения.
