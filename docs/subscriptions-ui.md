# Подписки: серверный обзор и Windows UI

Windows 0.11.0 / backend 0.10.0: GET /billing/overview, POST /billing/operations и
GET /billing/operations/{id} реализованы. Операции и идемпотентность хранятся в
PostgreSQL. Заменяемый provider port проверен на изолированном тестовом провайдере.
В работающем development backend adapter не подключён: новые операции отвечают
503 BILLING_DISABLED, actions=[], реальные списания выключены. Endpoint операции
читает сохранённый результат; повтор уже принятого запроса работает и без adapter.

В 0.8.0 добавлен явно включаемый development/test адаптер с сохранённым журналом
и служебными уведомлениями: [инструкция sandbox](billing-sandbox.md).
По умолчанию он выключен; его наличие не означает включение в развёрнутом backend.

В 0.9.0 усилены RENEW/CHANGE_METHOD/CANCEL и подтверждение состояния тестовых
разрешений (миграция 0026). Продление сохраняет действующее разрешение, смена
отзывает прежнее, отмена сохраняет обе даты оплаченного периода. Полные правила
и управление тестовым адаптером — в [billing-sandbox.md](billing-sandbox.md).


## Реализованный серверный обзор — 0.6.0

### Возможности маршрутов — 0.10.0

Overview дополнен `provider_mode` (DISABLED/SANDBOX/LIVE) и `payment_routes`:
четыре объекта `{id,currencies,recurring_currencies}` для MIR, BANK_CARD,
ALIPAY_WECHAT и CRYPTO. Recurring currencies — подмножество доступных валют;
wallets/crypto не получают recurring mandate. Возможности задаёт адаптер,
а не Windows. Без адаптера коллекции валют пусты. При продлении они ограничены
валютой договора. Матрица включена в revision; смена требует нового согласия.

Тестовый адаптер: MIR — RUB с автопродлением; BANK_CARD — RUB/USD с автопродлением;
ALIPAY_WECHAT/CRYPTO — USD, разовая оплата. Это синтетическая конфигурация,
не обещание возможностей реального провайдера/merchant account. Backend проверяет
матрицу, а accepted quote сохраняет recurring terms для последующего восстановления.
Старые provider requests читаются без нового необязательного поля.

Windows разрешает POST-действия/внешний переход только при явном LIVE,
operations_available и account actions. Live adapter пока отсутствует; guard
принимает только sandbox, поэтому реальные платежи недоступны. Sandbox API/CLI
остаётся для изолированных тестов, Windows SANDBOX read-only. Старый backend без
полей возможностей также read-only; противоречивые матрицы отклоняются.

GET `/billing/overview` требует действующую Bearer-сессию и берёт account ID только
из неё. Запрос не принимает доверенные group/user/price/date параметры. Ответы,
включая ошибки, имеют Cache-Control: no-store и Vary: Authorization. Недействительная
сессия → 401 AUTH_INVALID, блокировка/отзыв → 403, недоступность данных →
503 BILLING_UNAVAILABLE. Никакой выдачи чужого snapshot или демонстрационного fallback.

Одна SQL-выборка читает подписку, принадлежность группе, каталог и фиксированную
цену в согласованном MVCC-снимке. Эффективный plan вычисляется тем же доменом,
что `/me` и VPN. ACTIVE означает действующий оплаченный период с автопродлением;
CANCELED — действующий период без него; EXPIRED — сохранённый платный договор без
действующих прав. Окончание периода исключительно. Реальный флаг auto_renew
сохраняется и при EXPIRED: отсутствие оплаченных прав не подтверждает отмену у провайдера.

`current_price` берётся только из `subscription_prices`, а не из текущего каталога.
У старых/ручных подписок без подтверждённой цены — null и «сведения недоступны».
`payment_method=null` означает отсутствие достоверных реквизитов: флаг автопродления
сам по себе не позволяет восстановить платёжный способ. В этом выпуске ничего не
отменяется у провайдера и не обещается прекращение уже настроенных списаний.

`revision` — непрозрачный SHA-256 от идентичности/updated_at подписки, группы,
ревизии каталога и фактического ответа. Он стабилен для двух устройств аккаунта и
перезапуска сервера. Изменение каталога, группы, снимка цены, состояния подписки,
наступление/окончание предложения или оплаченного срока меняет ревизию.
Обычный ход времени внутри неизменного состояния её не меняет.

### Каталог, группы и периоды

Миграция `0023_billing_catalog` добавляет:

- `client_groups`: новая сущность UUID + имя; default ID
  `e3a7f90a-983a-4d5d-8f93-4d536e00be01`;
- `client_group_memberships`: один group ID на account (не на устройство).
  Отсутствие назначения означает default; чужой группе default-цены не подставляются;
- `billing_catalog`: атомарный версионированный JSON v1 в PostgreSQL;
- `subscription_prices`: неизменяемый снимок договора с subscription ID, offer ID,
  group ID, catalog revision, валютой, суммой и locked_at. UPDATE запрещён DB trigger.

Владелец разрешил временные рабочие месячные цены Premium: RUB 19900 коп.
(обычная 29900), USD 299 центов (обычная 399). Они однократно посеяны миграцией,
затем полностью управляются БД. В React/Python-сервисе нет запасных цен.
Это предложение default-группе с 2026-01-01 UTC без конечной даты.
Free не продаётся; Platinum назначается вручную, имеет права Premium и не получает
покупных предложений или выдуманных преимуществ.

Формат закрытого каталога:

```json
{
  "schema_version": 1,
  "entries": [{
    "group_id": "e3a7f90a-983a-4d5d-8f93-4d536e00be01",
    "valid_from": "2026-01-01T00:00:00Z",
    "valid_to": null,
    "offer": {
      "id": "eb54867b-5954-4b07-9690-560d4fbd4155",
      "plan": "PREMIUM", "period": "MONTH",
      "prices": {
        "RUB": {"amount_minor": 19900, "original_amount_minor": 29900},
        "USD": {"amount_minor": 299, "original_amount_minor": 399}
      }
    }
  }]
}
```

`valid_from` включительно, `valid_to` исключительно (null — без срока), обязательны
timezone-aware даты. Пересечения одной группы и повторяющиеся offer ID отклоняются;
соседние интервалы разрешены. Между интервалами предложение отсутствует. Целые
минимальные единицы >0, без конвертации; обе валюты обязательны, старая цена null
или строго больше текущей. Новое коммерческое предложение получает новый offer ID.

Публикация только доверенным оператором из backend-окружения:
`python -m prettylisavpn.billing.catalog /secure/catalog.json --expected-revision <UUID>`.
CLI валидирует всю замену, существование group ID, serializes concurrent publication
и проверяет CAS; неизменный документ сохраняет ревизию. Конфликт/ошибка откатывает
транзакцию. Нет публичного admin/mutation API. Новую группу и назначения создаёт
доверенный DB-оператор, например в транзакции с
`SELECT pg_advisory_xact_lock(903115991)`, затем INSERT `client_groups` и UPSERT
`client_group_memberships` по user_id. Назначение не выдаёт платных VPN-прав.

Внутренняя граница `lock_contract_price` принимает только действующий Premium,
актуальные group/date/offer/revision и фиксирует выбранную валюту в транзакции
подтверждения договора. Повтор того же подтверждения возвращает прежнюю цену;
замена валюты/offer/revision уже зафиксированного договора отклоняется. Смена
каталога/группы и отмена автопродления не переписывают снимок.
В нём сохранены обе валюты и условия скидок: действующий Premium получает в offers
свой снимок, даже после окончания акции. Новые предложения группы показываются
Free/expired; действующему договору без снимка не подставляется текущая цена. Граница 0.6.0 остаётся для старых снимков; операции 0.7.0 фиксируют принятую цену
в append-only billing_contracts атомарно с подтверждённым результатом. Реальное
оформление у платёжного сервиса ещё не включено.
Для старых договоров цена не восстанавливается из нового каталога. Смена цены
действующего договора недопустима; новая коммерческая договорённость требует
отдельного подтверждённого договора, а не UPDATE snapshot.

Windows сохраняет выбор валюты отображения отдельно от фиксированной валюты договора.
При payment_operations_available=false очищает устаревший локальный pending ID,
не опрашивает операции, не открывает checkout/провайдера и не вызывает POST.

## Интерфейс

Общий заголовок PrettyLisaVPN, Rubik и палитра сохранены. Страница содержит
возврат в настройки, заголовок, обновление и две светлые карточки:

- тариф, оплаченный срок, текущая цена, автопродление, месячные предложения;
- платёжный способ, изменение/привязка и отмена подписки.

У free/expired основное действие — «оформить подписку»; у active/canceled —
«продлить подписку». При продлении backend должен создать операцию с подтверждением
у провайдера и возможностью привязать новый платёжный способ. Это может быть
карта, кошелёк или любой поддерживаемый способ, а не только банковская карта.
Пользователь видит текущий оплаченный тариф и стоимость отдельно от цены
следующего месяца. Для действующего тарифа используются предложения этого тарифа.
Неизвестные будущие уровни показываются по коду, premium — со ⭐, platinum — с 💎.

Цены не вычисляются через конвертацию: backend присылает отдельные суммы RUB/USD
в минимальных единицах валюты, один период MONTH. original_amount_minor бывает
null либо строго больше amount_minor; старая цена зачёркивается для каждой валюты
отдельно. Обе валюты видны, выбранная — крупнее. Клиент не содержит рабочих цен.

Отмена требует отдельного подтверждения: доступ до paid_until сохраняется,
автопродление выключается, повторное использование платёжного способа отзывается.
Успех не показывается до терминального результата backend; ошибка не снимает
подписку локально. После подтверждения клиент перечитывает snapshot. Недоступность
API/цены не заменяются фиктивным тарифом, суммой или платёжным способом.

## Основная валюта

Выбор владельца: последняя страна до подключения VPN. RU → RUB, остальные → USD.
Если страна ещё неизвестна, USD; выбор можно изменить вручную. Ручной выбор имеет
приоритет и сохраняется отдельно для аккаунта. Автоматическое наблюдение работает
на уровне приложения, а не только Home. Оно сохраняет только ISO-код страны,
не IP/город/координаты и не историю.

Запрос разрешён только при phase=DISCONNECTED, backend=NONE, tunnel=DOWN.
При смене состояния запрос отменяется; результат принимается только если объект
состояния VPN остался тем же. Во время VPN, подключения/проверки, деградации или
неизвестного состояния не определяем и не перезаписываем исходную страну. Обновление
раз в минуту и при online/focus. Для смены цены VPN никогда не отключается.

Это определение исходящей страны при отключённом PrettyLisaVPN, а не доказательство
физического проживания. Другой системный VPN/прокси или старая сохранённая страна
могут повлиять на результат; ручное переключение всегда доступно. Backend не должен
использовать этот клиентский выбор для прав доступа, налогов, антифрода или определения
допустимого способа оплаты: это только предпочтение отображения/валюты операции.

## Общий контракт (API реализован; реальный провайдер выключен)

Все запросы авторизуются Bearer access token, без cookie, cache и логирования
реквизитов/платёжных URL. Реквизиты и секреты провайдера никогда не проходят через UI.
Отдельный BillingClient не меняет прежний ApiClient и заменяется в тестах.

GET /billing/overview:

```json
{
  "payment_operations_available": false,
  "revision": "opaque-snapshot-version",
  "pending_operation_id": null,
  "plan": "PREMIUM",
  "status": "ACTIVE",
  "paid_until": "2099-11-17T20:59:59Z",
  "auto_renew": true,
  "current_price": { "amount_minor": 29900, "currency": "RUB" },
  "payment_method": null,
  "offers": [{
    "id": "opaque-offer-id",
    "plan": "PREMIUM",
    "period": "MONTH",
    "prices": {
      "RUB": { "amount_minor": 29900, "original_amount_minor": null },
      "USD": { "amount_minor": 399, "original_amount_minor": null }
    }
  }],
  "actions": []
}
```

Суммы и дата в примере синтетические, не продуктовые расценки. Статусы:
FREE, ACTIVE, CANCELED (автопродление отменено, доступ ещё оплачен), EXPIRED.
Backend определяет актуальность срока по серверному времени. У FREE нет оплаченного
срока/текущей цены; у ACTIVE/CANCELED paid_until обязателен. CANCELED требует
auto_renew=false и payment_method=null. Actions — реальные доступные возможности,
сервер независимо проверяет каждую из них. Pending ID позволяет восстановиться
после перезапуска или запроса с неопределённым исходом.

POST /billing/operations:

```json
{
  "action": "SUBSCRIBE",
  "payment_route": "MIR",
  "request_id": "client-generated-uuid",
  "expected_revision": "opaque-snapshot-version",
  "offer_id": "opaque-offer-id",
  "currency": "RUB"
}
```

Action: SUBSCRIBE, RENEW, CHANGE_METHOD, CANCEL. У последних двух offer_id=null.
Цена/скидка/сумма списания никогда не передаются клиентом. Backend атомарно проверяет
аккаунт, revision, предложение, валюту, возможности и незавершённую операцию.
Старая revision → 409; при изменении цены нужно новое согласие пользователя.
Для одного аккаунта одновременно допустима только одна незавершённая операция.

Request ID — идемпотентный ключ в пределах аккаунта. Повтор с тем же телом возвращает
ту же операцию; другое тело с тем же ключом отклоняется. Клиент сохраняет ключ на
повторную попытку/навигацию, блокирует двойное нажатие и не создаёт новый платёж
после timeout. Backend обязан сохранять результат/идемпотентность достаточно долго
для восстановления, а не полагаться на этот UI guard. Endpoint обзора возвращает
незавершённую операцию независимо от устройства. Неопределённый исход не означает
ни успеха, ни отсутствия платежа.

Ответ POST и GET /billing/operations/{id}:

```json
{
  "id": "opaque-operation-id",
  "status": "PENDING",
  "redirect_url": "https://configured-payment-host.example/confirmation"
}
```

Статусы PENDING, SUCCEEDED, FAILED, CANCELED; redirect_url может быть null.
ID принадлежит только текущему аккаунту. Backend хранит терминальный результат,
проверяет подпись/идемпотентность вебхука и сверяет провайдера. Клиент опрашивает
операцию каждые 3 секунды до 90 секунд, далее при focus/обновлении. Незавершённая
операция блокирует новые действия; можно повторно открыть подтверждение. В session
storage сохраняются только непрозрачные ID/ключи, не redirect URL или реквизиты.

Возврат из браузера, URL callback, клик и локальная успешная навигация не меняют
оплаченные права. При терминальном результате перечитывается GET overview.
Цена/дата/платёжный способ меняются только по новому ответу backend. До внедрения
deep link пользователь возвращается в приложение сам; focus и «обновить» проверяют
результат. Никакого success=true из браузера клиент не принимает.


## Устойчивые операции — backend 0.7.0

Миграция `0024_billing_operations` добавляет `billing_operations` (запрос, fingerprint,
неизменяемая quote, provider name, статус, lease/fencing, попытки), `billing_accounts`
(текущий договор и безопасная подпись способа оплаты, закрытый opaque mandate ID)
и append-only `billing_contracts`. Старые `subscription_prices` сохраняются;
новый договор после окончания прежнего не переписывает историческую цену.

POST возвращает 200 с `{id,status,redirect_url}` как для первого принятия, так и
для повтора. Request ID — UUID, область уникальности `(account_id, request_id)`.
Fingerprint включает все нормализованные поля команды, включая revision/route/
валюту; другой payload с тем же ключом → 409 BILLING_IDEMPOTENCY_CONFLICT.
Идемпотентность сохраняется на срок жизни аккаунта, включая терминальные результаты.
Повтор проверяется **до** текущей revision, наличия adapter и доступности действий:
потерянный ответ не становится новой операцией после смены цены или перезапуска.

Новый запрос атомарно проверяет актуальную overview revision, group/date/offer,
валюту, действие и поддержку route/currency adapter. Клиентская сумма/цена/provider
URL запрещены схемой. Старая revision → 409 BILLING_REVISION_CHANGED, недоступное
действие/offer/route → соответствующий BILLING_* код с 409. Активный договор
продлевается только в своей зафиксированной валюте (BILLING_CURRENCY_LOCKED при
попытке смены), обе цены/скидки снимка сохраняются. Platinum не продаётся.
Действующие legacy-договоры без подтверждённой цены/известного mandate не получают
выдуманные возможности или новый способ оплаты вместо неизвестного старого.

Блокировки при принятии упорядочены так же, как публикация каталога; частичный
UNIQUE index разрешает только один PENDING на аккаунт. Другой ключ в это время →
409 BILLING_OPERATION_IN_PROGRESS. Внешний вызов начинается **после commit** admission;
при сбое БД до commit он не выполняется. Quote содержит выбранные условия, поэтому
изменение каталога/группы после принятия не меняет уже подтверждаемую сумму.

Provider получает стабильный UUID операции, не новый ключ на каждую попытку.
`BillingProvider.supports` задаёт допустимые action/route/currency;
`reconcile` идемпотентно создаёт/находит и сверяет результат по этому UUID.
Adapter обязан удостоверять внешние ответы и не создавать повторный платёж после
истечения собственного idempotency window: при неизвестном результате требуется
сверка исходной операции, а не новый charge. Provider name сохранён в операции;
другой adapter не получает её или чужой mandate. Live adapter/загрузка credentials
не поставляются; разрешены только явно внедрённые sandbox adapters в тестах.

Timeout, недоступность provider и неопределённый исход остаются PENDING.
Worker с ограниченным timeout и durable lease возвращается к той же операции;
после падения процесса другая инстанция продолжает после истечения lease. Fencing
не позволяет старому worker применить результат после нового. Backoff сохраняется
в БД, worker не держит транзакцию во время внешнего IO. POST/GET могут ускорить
сверку; фоновый worker восстанавливает работу и без открытого клиентского экрана.

GET проверяет принадлежность аккаунту **до** обращения к provider. Чужой или
неизвестный UUID → 404 BILLING_OPERATION_NOT_FOUND; malformed body/ID → 422
validation_error без входных значений. Общие auth/cache правила действуют для обоих
endpoint. Ответ никогда не содержит quote, mandate ID, попытки, provider credentials
или внутреннюю ошибку. Redirect разрешён только HTTPS/443 с точным allowlist хоста,
без credentials/fragment/control characters; никакой произвольной навигации.

Overview возвращает pending_operation_id независимо от устройства; наличие pending
убирает новые actions. Если adapter временно отключён, сохранённый pending остаётся
доступен для восстановления: payment_operations_available=true означает, что
клиент может читать его статус, но actions=[] запрещает новые операции. Без adapter
и pending флаг false. Терминальный результат снимает pending и меняет revision.

SUCCEEDED сохраняется в одной транзакции с подпиской, договором и способом оплаты.
Проверяются UUID receipt, точная сумма/валюта, применимость mandate к маршруту и
подтверждённый отзыв прежнего mandate при замене. Для CANCEL обязательны отдельные
подтверждения остановки recurring и отзыва mandate. До них и до commit успеха нет;
срок оплаченного доступа не сокращается. FAILED/CANCELED освобождают pending только
при авторитетном терминальном результате adapter и не дают платных прав.

Месяц — календарный UTC месяц с ограничением дня последним днём следующего месяца.
RENEW добавляет месяц после max(now, paid_until), повтор не добавляет второй период.
SUBSCRIBE начинает новый договор; действующий договор сохраняет свою immutable
цену. Рекуррентный статус берётся только из подтверждённого mandate; CRYPTO и
ALIPAY_WECHAT не получают выдуманного автопродления. /me и VPN читают ту же подписку.

Если подписка вручную изменена, пока provider подтверждал операцию, worker не
переписывает новые права/срок: сохраняет PENDING/SUBSCRIPTION_CHANGED для закрытой
операторской сверки. Нельзя объявить FAILED или запустить новый платёж, поскольку
provider уже мог принять деньги. Публичного force-success/reset endpoint нет.
Возврат, URL callback, клиентский клик и таймер не подтверждают оплату.

Проверки: PostgreSQL + настоящий JWT/auth HTTP, конкурентные ключи, повтор с другого
устройства/после нового service instance, потеря ответа после provider acceptance,
rollback local apply, crash/lease expiry/fencing, неподтверждённая отмена, неверный
receipt/redirect, смена каталога, сохранение paid_until и immutable DB guards.
Provider ledger изолирован и симулируется: это не проверка банковского списания.
Точные HEAD/run/attempt, полный CI и development smoke фиксируются в task PR.

## Внешнее подтверждение

Windows открывает URL через ShellExecuteW в системном браузере. Новый native command
принимает только HTTPS, порт 443, без credentials/fragment, с точным совпадением хоста
в VITE_PAYMENT_ALLOWED_HOSTS. Та же проверка выполняется в клиентском адаптере.
Никакой shell/командной строки и произвольных URI schemes; URL не журналируется.

VITE_PAYMENT_ALLOWED_HOSTS — список точных hostname через запятую, задаётся до сборки
React и Rust. По умолчанию пуст: до выбора провайдера внешняя навигация закрыта.
Не добавлять широкие wildcard/subdomain разрешения и хосты из произвольного ответа
backend. При реальной интеграции закрепить фактические домены выбранного провайдера,
проверить все redirect-переходы и тестовое/боевое окружения. Секретов в VITE нет.

## Backend follow-up

GET billing и каталог реализованы в 0.6.0; durable operations/provider port — в 0.7.0.
Для реальных списаний нужны отдельно согласованный live adapter, его credentials,
подтверждения/вебхуки, сверка и эксплуатационные процедуры.
Backend 0.5.0 отделяет отмену автопродления от оплаченного срока: CANCELED сохраняет
платные права до paid_until, после чего эффективный тариф становится Free. Это также
применяется к открытым VPN-сессиям. Ручной Platinum имеет права Premium; Free теперь
без рекламы с общим часом в сутки UTC. Точный действующий контракт и ограничения:
[subscription-entitlements.md](subscription-entitlements.md). API операций реализован, live provider по-прежнему не включён.

Отмена считается SUCCEEDED только после прекращения рекуррентных списаний и отзыва
действующего платёжного mandate/token у провайдера. Удаление лишь локальной подписи
способа оплаты недостаточно. Разобрать гонку с уже начатым списанием: сервер должен
обеспечить обещание «новых списаний не будет», не сообщать ложный успех при частичном
сбое и компенсировать/возвращать конфликтующий платёж согласно выбранному провайдеру.
Продление учитывает оплаченный остаток, исключает двойное списание/добавление периода.

локального успеха после redirect, недоступность, allowlist и валюту. Native capture

## Выбор платёжного маршрута (Windows 0.6.0)

Перед SUBSCRIBE/RENEW открывается «как оплатить»: четыре radio-карточки с иконками.
MIR — карта «мир»; BANK_CARD — банковская карта (Visa, Mastercard, UnionPay,
American Express), без названия «иностранная»; ALIPAY_WECHAT — Alipay/WeChat Pay;
CRYPTO — криптовалюта. Названия — категории/маршруты, не зашитые API конкретных
провайдеров. Их сопоставление настоящим сервисам выполняет будущий backend.

Приоритет у выбранной валюты: RUB → MIR первым и выбранным, USD → BANK_CARD.
Регион до VPN определяет начальную валюту; если пользователь переопределил её,
явный выбор важнее региона. При неизвестной стране применяется существующий USD.
После открытия modal предложение, revision и валюта фиксированы; обновление
геолокации в фоне не меняет подтверждаемые условия. Переключение radio ничего не
отправляет. Назад/Escape закрывают окно без операции/редиректа. Только «перейти к
оплате» создаёт операцию с payment_route и открывает её backend redirect URL.

BillingCommand.payment_route обязателен: MIR, BANK_CARD, ALIPAY_WECHAT или CRYPTO
для SUBSCRIBE/RENEW; null для CHANGE_METHOD/CANCEL (эти flows пока не менялись).
Маршрут входит в fingerprint ключа запроса: тот же ключ не должен использоваться
для другого выбранного способа. Цена/скидка не передаются клиентом. Backend обязан
проверять route, валюту, предложение, доступность провайдера и revision; произвольные
клиентские provider URL/merchant ID не принимаются. Выбор маршрута не является
подтверждением оплаты и не меняет уже привязанный способ.

Четыре варианта сейчас показываются в UI как предусмотренные продуктом категории.
Реальная доступность валют/маршрутов, курс/комиссии, одноразовость или возможность
автопродления (особенно для криптовалюты/кошельков) подтверждаются будущим backend
и провайдером. UI не должен придумывать рекуррентное списание или сохранённый mandate
для сервиса, который их не поддерживает. Интеграция и реальные платежи отложены.
