# Средняя скорость активного пользователя

## Компоненты и совместимость

Backend **0.36.0 → 0.37.0**, dashboard **0.6.3 → 0.7.0**: новая
метрика и административный API. Managed engine **0.6.0 → 0.6.1**:
более частая публикация существующих счётчиков. Версии клиентских приложений
не меняются. Миграция `0047_active_user_speed` добавляет две таблицы; существующие
контракты, VPN-сессии, авторизация и биллинг не меняются.

График находится в `/dashboard/#active-user-speed`, перед существующей историей
проверок. Оба направления подписаны **с точки зрения пользователя**. Действуют
общие фильтры группы/сервера; внутри блока можно выбрать несколько серверов выхода.
Посредники исключаются, чтобы relay-трафик не считался дважды.

## Сбор и формула

`TrafficWorker` работает в существующем fleet-worker независимо от длительных
синтетических проверок. Каждые пять секунд он параллельно опрашивает узлы через
существующий SSH transport с закреплёнными host keys и inventory. Новый helper
action `traffic` возвращает только UUID клиентской аренды, поколение счётчика,
UTC/monotonic-время и накопленные байты. Приватные ключи, IP клиентов,
назначения, DNS и содержимое пакетов не передаются и не логируются.

- WireGuard: `wg show pl-wg0 transfer`, только peers из клиентского журнала.
  Server TX = скачивание пользователя; server RX = загрузка. Это согласуется с
  [форматом WireGuard tools](https://git.zx2c4.com/wireguard-tools/tree/src/show.c).
- Остальные движки и browser proxy: существующие счётчики каждой аренды из
  защищённого `.stats`. Node engine публикует их раз в секунду, чтобы опрос раз
  в пять секунд не читал чередующиеся устаревшие значения. Supervisor записывает
  новое поколение при каждом старте процесса. На старых активных supervisor
  данные остаются неполными до обычного пересоздания сессии.
- Backend сопоставляет аренду с аккаунтом через `client_wireguard_leases`.
  Данные мониторинговых peers и интерфейсные счётчики в числитель не входят.

Сохраняются **неотфильтрованные дельты** отдельных подключений с границами
фактических интервалов. При чтении выбранные серверы фильтруются до расчёта.
Интервалы делятся по сетке UTC в пять секунд с пропорциональным распределением
байтов; внутри исходного интервала предполагается равномерный поток — более
точная форма коротких всплесков по накопленным счётчикам неизвестна.

В каждом окне суммируются байты всех подключений аккаунта. Время — объединение
перекрывающихся интервалов, а не сумма времени устройств. Направление активно
только при `bytes * 8 / seconds > FLEET_ACTIVITY_THRESHOLD_BPS` (по умолчанию
10 000 бит/с, десятичные Кбит/с). Ровно 10 Кбит/с не проходит порог. Неактивные
байты и секунды исключаются. Порог применяется при чтении и одинаково
пересчитывает выбранную историю после изменения настройки.

В точке: `sum(active bytes) * 8 / sum(account active seconds) / 1_000_000`.
Это среднее, взвешенное временем активности: более долго активный пользователь
имеет больший вес. Для медианы сначала рассчитывается скорость каждого аккаунта
за всю точку; каждый активный аккаунт имеет один голос. Готовые средние и медианы
серверов/минут не усредняются. При отсутствии активности оба значения `null`.

Сутки: до 289 пятиминутных точек. Неделя: до 169 часовых.
Час (60 минутных точек) сохранён в API для совместимости, но убран из UI в 0.8.0.
На границах окна блоки могут быть короче; текущий блок содержит только
завершённые минуты, с 15-секундным запасом на доставку последнего замера.
Полнота делится на фактическую длительность блока, указанную в подсказке.
Все периоды пересчитываются из исходных интервалов, включая точную медиану
сохранённых пользовательских скоростей. История и baseline хранятся восемь дней,
очистка выполняется сборщиком каждый час. Аккаунтные UUID не возвращаются в API.
Первая неделя после включения закономерно содержит пробелы.

## Полнота, сбросы и сравнение

Новая аренда/peer, boot ID, индекс интерфейса или поколение managed-процесса,
уменьшение любого счётчика, немонотонное время и разрыв **более 7,5 секунды**
создают новую baseline без трафика. Накопленный счётчик никогда не принимается
за дельту. Первый и последний неполные интервалы подключения не восстанавливаются.
Clock skew узла относительно backend более 7,5 секунды отклоняется; UTC и
monotonic-разница проверяются совместно. NTP на узлах обязателен.

PostgreSQL блокирует cursor узла в транзакции. Одинаковые/более старые snapshots
не применяются повторно; обновление baseline и запись дельты атомарны.
Рестарт сборщика использует durable baseline, разрывы не считаются активностью.
Потерянный конечный счётчик удалённой аренды не угадывается.

Подсказка показывает среднюю, медиану и число уникальных активных аккаунтов
отдельно для двух направлений, полностью/частично покрытые серверы и долю
подтверждённого времени серверов. Неизвестная аренда, отсутствующий ожидаемый
peer, новый/reset counter и устаревший managed sample делают интервал неполным.
Корректные дельты остальных подключений сохраняются, но график отмечен как
неполный. Отсутствие данных не заменяется нулём или последним значением.

Существующий показатель — **результат синтетической межсерверной проверки**,
не теоретический максимум линии или гарантированная скорость пользователя.
Вторая линия сохраняет текущую семантику dashboard: медиана последних
синтетических результатов каждого выбранного сервера в том же временном блоке.
В блоках без проверок значение отсутствует; с dashboard 0.8.0 линия визуально
соединяет известные точки через такие пропуски. Процент `mean / reference * 100`
показывается только при полной выборке с обеих сторон и положительном ориентире.
Он может превышать 100% и не означает загрузку канала.

## API, rollout и проверка

`GET /admin/monitoring/active-user-speed?period=1h|24h|7d&node_ids=UUID&node_ids=UUID`
использует существующие fleet reader/admin credentials. Caddy публикует только
GET `/dashboard/api/active-user-speed` под прежним HTTPS Basic login; monitor
token подставляется на сервере. В JavaScript секретов нет. Нет нового публичного
ingest endpoint и нет нового слушающего сервиса на VPN-узлах.

Rollout: применить миграцию, обновить backend/fleet-worker, установить node helpers
существующим Ansible `fleet/ubuntu/configure.yml`, поставить проверенный
`pl-node-engine` этой сборки и dashboard/Caddy route. Порог задаётся в fleet.env
для API (сбор сохраняет исходные дельты). Не выполнять реконфигурацию клиентов
или принудительный разрыв их сессий ради метрики. Старый helper возвращает
неподдерживаемый action, что отображается как неизвестные данные до обновления.
Rollback приложения допустим с сохранёнными новыми таблицами; откат миграции
удалит историю метрики и не нужен для отката приложения.

Локально проверены формулы, направления адаптеров, настоящая PostgreSQL
миграция/metadata, конкурентные дубли, восстановление, фильтры, retention и
авторизация. Общий интеграционный набор: 255 passed / 1 conditional skip.
Полный Linux unit-run из Git-архива: 730 passed, 27 subtests. Windows-specific
ограничения bash/архивных timestamps не воспроизводятся в Linux checkout. Dashboard: 25 тестов и TS/Vite build.

7 ноября 2026 проверены реальные development-счётчики: временный аккаунт,
два устройства и две клиентские WireGuard-аренды на DE/NL; US опрашивался без
нагрузки. Получены 93 snapshot (31 опрос × 3 узла), без ошибок SSH. Шесть
контрольных передач прошли; последние две проверки завершились после истечения
тестовых setup-аренд. Обе аренды удалены штатно, временные auth-сессии отозваны,
ключи и network namespaces очищены. Аккаунт и закрытые аренды остаются обычными
аудиторскими записями; пользовательские подключения не менялись.

Snapshot воспроизведены через новый ingest → PostgreSQL → защищённый API →
собранный dashboard. Это реальные тестовые байты, не демонстрационные числа.
В минуте 11:21 UTC: download 2,137528 Мбит/с, upload 0,753869 Мбит/с, один
уникальный аккаунт в обоих направлениях, полнота 87,5929%. Объединение двух
активных минут даёт 2,532703 / 1,877721 Мбит/с, а не среднее минутных скоростей.
Проверены все три периода, фильтр DE и пустой выбор, desktop/mobile layout,
подсказка и отсутствие ошибок browser console. [Скриншот реального прогона](evidence/active-user-speed-real-counters.jpg).

## Dashboard 0.8.0 — управление графиком

Отдельная UI-задача: dashboard **0.7.0 → 0.8.0 (MINOR)** — добавлено управление
масштабом. Backend остаётся **0.38.0**, engine **0.6.1**; клиенты, схема БД,
сбор счётчиков, порог активности, формулы и авторизация не меняются.

В UI осталось два периода: **24 часа — мониторинг** (выбран по умолчанию) и
**7 дней — аналитика**. API продолжает принимать `1h` для совместимости.
Все известные точки каждого ряда соединены, включая соседние известные точки
по разные стороны пропуска. Такая линия — только визуальная связь: ни нули,
ни интерполированные значения, ни последнее известное значение не записываются
в отсутствующие интервалы. Их подсказки и индикатор полноты остаются прежними.
Начало/конец ряда за пределы первого/последнего замера не продлеваются.

Каждое направление имеет независимый выбор **Ось Y**:

- **Авто** — обе линии помещаются в шкалу с запасом 10%.
- **По фактической скорости** — верхняя граница определяется средней скоростью.
- **Вручную** — верхняя граница в Мбит/с, минимум 0,001; принимаются запятая
  и точка. Нижняя граница всегда ноль. Ошибка ввода сохраняет предыдущую шкалу.

Значения выше шкалы обрезаются в SVG, а не прижимаются к верхней границе;
подсказка сохраняет истинные числа и проценты. Рядом появляется пояснение,
как вернуть все точки через «Авто». Автообновление сохраняет масштаб;
при смене периода/набора серверов начинается новый просмотр со шкалой «Авто».
Области выбора соседних пятиминутных точек больше не перекрываются.

Проверено локально: `npm ci`, 28 tests, TypeScript `tsc --noEmit`, Vite build,
`git diff --check`. Отдельных lint/format-команд у dashboard нет.
Browser QA воспроизводит **реальные ответы защищённого development API**,
полученные 8 ноября 2026 около 12:11 UTC: 289 точек суток, 169 точек недели,
все три выхода и отдельно DE. Проверены оба периода, выбор всех/одного/ни одного
сервера, независимость осей, масштаб по средней, ручные 2,5 и 0,001 Мбит/с,
ошибочный ввод, подсказка в пропуске, clipping и экраны 1280×1100 / 390×844.
Ошибок browser console не обнаружено. Это локальная сборка на настоящих
агрегатах, не демонстрационные числа и не заявление о deployment нового UI.
