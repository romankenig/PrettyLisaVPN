# Проверка завершения GitHub Actions

Эта инструкция дополняет [AGENTS.md](../AGENTS.md) и
[правила изменений](versioning.md). Исправление CI не меняет продуктовую версию:
Windows остаётся 0.2.0, backend source version — 0.1.0.

## Причина ошибок Windows window capture

Старый workflow запускался на push capture-скриптов, скачивал exe из фиксированного
Actions run 38885090336 и применял к нему сценарий из нового checkout.
Например, новый сценарий ожидал frontend 0.2.0 и новый sidebar, а бинарник
показывал прежний интерфейс. Run 38941086981 завершился timeout на ожидании 0.2.0.
Более ранние изменения рамки и Rubik также были несовместимы с этим старым exe.

Основной Windows UI review при этом мог успешно собрать и проверить новый код.
Проверка только pull_request-запусков пропускала отдельный push-workflow.
В истории ветки выявлены два семейства ошибок: основные Windows проверки
(форматирование, ожидания тестов, очистка WebView2; исправлены ранее) и повторявшееся
использование старого exe во вспомогательной съёмке.

## Исправленная схема

- Windows UI review поддерживает pull_request, workflow_dispatch и workflow_call.
  Один общий job выполняет frontend checks, форматирование, locked metadata,
  нативную сборку, capture и загрузку артефактов.
- Windows window capture вызывает этот job через локальный reusable workflow
  из текущего commit. Старый download-artifact, run_id и исторический exe удалены.
- Основной PR workflow остаётся автоматической проверкой UI/capture-скриптов.
  Отдельный capture workflow запускается вручную либо при изменении собственного
  или общего workflow-файла в текущей review-ветке; повторный автоматический запуск того же
  сценария на каждое изменение скрипта больше не нужен.
- Артефакты каждого запуска содержат новый exe и его фактические SHA/run/attempt.
  Различать push SHA и временный PR merge SHA; проверяемый source head должен совпадать.
- Export UI screenshots — отдельная утилита экспорта PNG из явно выбранной старой
  сборки. Она не подтверждает проверку нового commit. Backend/deploy и другие
  workflow сохраняют собственные условия запуска.

## Устойчивость native capture и повторного запуска

В проверочном run 38942299970 выявлен timeout запуска PowerShell helper:
spawnSync pwsh ETIMEDOUT при лимите 20 секунд. Helper загружает System.Drawing,
компилирует Win32 interop и снимает реальное окно. Его ограниченный timeout
увеличен до 60 секунд; проверки native region, стилей, размеров и непустого
снимка сохранены. Ошибка или превышение нового лимита по-прежнему проваливает job.

upload-artifact использует overwrite=true: повторный run/attempt может заменить
артефакт с тем же именем вместо конфликта. Метаданные содержат SHA/run/attempt,
поэтому при повторной проверке использовать именно последнюю успешную попытку.

## Обязательная проверка перед завершением задачи

1. Прочитать PR и зафиксировать фактический remote head SHA.
2. Получить общий список запусков Actions для ветки и этого SHA без фильтра по
   событию. Просмотреть все страницы. Учитывать push, pull_request, dispatch и
   jobs reusable workflow. Сопоставить список с triggers изменённых workflow.
3. Проверить все найденные runs до completed/success и все их jobs.
   Пропуск deployment вне develop ожидаем; пропуск quality/build/capture
   требуется отдельно расследовать. Не считать стадию успешной по одному
   загруженному артефакту или успешно завершённому capture-step: последующие
   cleanup/upload/post steps тоже могут завершить весь job ошибкой.
4. Сверить Checks API и commit statuses. Статусы старого commit, pending,
   in_progress и отменённый текущий запуск не подтверждают готовность.
5. После последнего push повторить проверку с новым head, даже если изменился
   только handoff. Когда нужен лишь итоговый отчёт о прошедших проверках,
   обновить PR description без нового commit.
6. Перед финальным ответом ещё раз сверить remote HEAD. Привести SHA,
   ссылки и результаты всех относящихся к задаче workflow. Если появился новый
   commit, проверить уже его; не выдавать результаты предыдущего за новые.

Для GitHub connector использовать общий GET-ресурс:

```text
https://api.github.com/repos/OWNER/REPO/actions/runs?branch=BRANCH&head_sha=SHA&per_page=100&page=1
https://api.github.com/repos/OWNER/REPO/commits/SHA/check-runs?per_page=100&page=1
https://api.github.com/repos/OWNER/REPO/commits/SHA/status
```

BRANCH и SHA берутся из актуального PR; параметры URL кодируются. При наличии
следующей страницы продолжать чтение. fetch_commit_workflow_runs предоставляет
только pull_request-triggered runs на первой странице и годится лишь как
дополнительная выборка. Логи загружать только для нужных jobs; base64 скриншотов
и содержимое секретов не выводить при поиске ошибок.

## Фиксация результата этой задачи

До push локально проверяются YAML, связь reusable caller/callee, отсутствие
исторического exe и сохранность обязательных build/capture шагов.
После push конечные статусы общего списка Actions и Checks API фиксируются
в описании PR и итоговом сообщении. Это позволяет проверить последний HEAD
без дополнительного docs commit, снова запускающего CI.
