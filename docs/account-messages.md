# Сообщения аккаунту — Windows 0.8.0 и общий API v1

Цель: сообщать пользователю об обновлениях, предложениях и других новостях
независимо от устройства. Содержание и наличие определяет backend по аккаунту.
Сейчас реализованы Windows UI и клиентский адаптер предложенного контракта.
Backend source 0.1.0 не менялся, messages endpoints/хранилище/управление ещё отсутствуют.

## Почему JSON

Каждая платформа отображает один смысл своими компонентами. V1 — заголовок,
абзацы, списки и типизированные кнопки. Нет HTML, Markdown с HTML, WebView-страниц,
JavaScript, произвольных URL, удалённых изображений или загрузки исполняемого кода.
React выводит содержимое текстом. Регистр содержимого сохраняется; название продукта
backend обязан писать PrettyLisaVPN. Компонент кнопки сохраняет его канонический регистр.

Неизвестный вид сообщения отображается как обычное сообщение. Неизвестный блок
заменяет всё содержимое на обязательный fallback_text. Неизвестное действие не
показывается; закрытие/подтверждение остаются доступны. Некорректная известная
структура/неподдерживаемая schema_version не показывает popup и не мешает входу.

V1 не реализует новые функции старого приложения: Windows до 0.8.0 вообще не
поддерживает эти сообщения. Новая схема/кнопка требуют поддержки соответствующих
клиентов. Backend должен фильтровать по поддерживаемой схеме и версии платформы.

## Предлагаемый контракт

После входа или восстановления авторизации:

```http
GET /messages?platform=WINDOWS&app_version=0.8.0&locale=ru-RU&schema_version=1
Authorization: Bearer <access-token>
```

У пользователя нет user_id в query/body: backend берёт аккаунт из токена.
Параметры контекста используются для отображения/совместимости, не дают прав
на тариф или платёж. Сервер независимо проверяет любые продуктовые действия.
Неавторизованный клиент сообщений не запрашивает. Ответ без cache/cookie:

```json
{
  "schema_version": 1,
  "messages": [{
    "id": "88888888-8888-4888-8888-888888888888",
    "revision": 1,
    "kind": "announcement",
    "title": "новости PrettyLisaVPN",
    "blocks": [
      {"type": "paragraph", "text": "содержание сообщения"},
      {"type": "list", "items": ["первый пункт", "второй пункт"]}
    ],
    "fallback_text": "содержание сообщения в текстовом формате",
    "primary_action": {"type": "OPEN_SUBSCRIPTION", "label": "посмотреть"},
    "dismiss_label": "понятно",
    "expires_at": null
  }]
}
```

Пустой messages означает отсутствие сообщений. Порядок задаёт backend по приоритету,
затем детерминированно; клиент его сохраняет. Допустимые kind: announcement, update,
promotion. UUID id + положительная целочисленная revision идентифицируют редакцию.
Повтор одного ключа запрещён. При новой редакции backend явно определяет повторный показ.
expires_at — ISO UTC/offset timestamp либо null, истёкшее сообщение не показывается.
Окно закрывается при истечении срока; это не подтверждение прочтения.

Лимиты V1: до 10 сообщений за запуск, title 120, dismiss/action label 60,
fallback_text 4000 символов, 1–12 blocks, paragraph до 3000 символов,
list 1–12 items по 500 символов. Текущий HTTP-адаптер дополнительно отклоняет JSON
длиннее 65536 символов после чтения. Это не потоковый лимит сетевого ответа;
ограничение размера на сервере/proxy обязательно. Остаток очереди сервер может
вернуть при следующем запуске, не перегружая пользователя десятками popup.

Разрешённые primary_action.type: OPEN_SUBSCRIPTION, OPEN_SETTINGS, OPEN_ABOUT.
Они отображаются в маршруты текущего клиента. Primary action может быть null/отсутствовать.
Произвольные пути, URL и код сервер передавать не должен. Для внешней страницы
обновлений/магазина в будущем нужен отдельный согласованный action и native
HTTPS-адаптер с ограничением адресов. Сейчас внешняя навигация не реализована.

После «понятно» или основной кнопки:

```http
POST /messages/88888888-8888-4888-8888-888888888888/acknowledgements
Authorization: Bearer <access-token>
Content-Type: application/json

{"revision": 1}
```

Успешный ответ:

```json
{"id":"88888888-8888-4888-8888-888888888888","revision":1,"acknowledged":true}
```

Backend обязан сделать ACK идемпотентным по (user_id, message_id, revision),
проверить доступ пользователя к сообщению и записать результат надёжно.
Повтор после timeout возвращает то же подтверждение; конфликт другой редакции
не должен отмечать новую редакцию прочитанной. Клиент сверяет все поля receipt.
До подтверждённого ответа окно не исчезает и внутренняя навигация не выполняется.
При ошибке — безопасное пояснение и повтор того же ID/revision, без сырого ответа.

Показ, GET, X, Escape и «позже» не отправляют ACK. «Позже» пропускает конкретное
сообщение только в текущем посещении, затем предлагает следующее из очереди.
Следующий вход/запуск снова спросит backend. Локальный постоянный read-флаг не
хранится; при успехе общим источником истины остаётся backend.

## Поведение Windows

Запрос начинается, когда есть активная авторизация, открыта основная часть
приложения и известна frontend SemVer. Не ждёт profile/Home и не блокирует вход.
Сохранённая авторизация при новом запуске тоже вызывает запрос. Refresh токена
или навигация между Home/Settings/About не создают новый запрос при той же сессии.

HTTP deadline 5 секунд; запросы отменяются при смене аккаунта/сессии и unmount.
Устаревшие ответы/ACK не меняют другой аккаунт. На login/OTP сообщений нет.
404/501 (API отсутствует), 401/403 и некорректная схема тихо отключают сообщения
в текущем посещении; сообщения не разлогинивают пользователя. Транспортный сбой
можно повторить при focus/online, не чаще раза в 10 секунд. После успешного списка
новых запросов в этом посещении нет. Регулярный polling/push — отдельная задача.

Окно — modal dialog в текущем native окне, с сохранением фокуса и прокруткой
длинного содержимого. Если открыто другое modal-окно, сообщения ждут его закрытия.
Система не предназначена для принудительной блокировки клиента/обновления.

## Будущий backend и кроссплатформенность

По умолчанию показывать редакцию один раз на аккаунт до явного подтверждения.
После подтверждения на Windows не возвращать её Android/iOS и другим клиентам
этого пользователя. Сами другие клиенты пока не реализованы; JSON-контракт общий.

Нужны модели и миграции: сообщения/редакции/локализации/периоды/приоритет/аудитория
и ACK пользователя. Аудитория может учитывать user_id, тариф, платформу и диапазон
версий конкретной платформы; SemVer Windows не сравнивается с SemVer Android.
Акции не подтверждают наличие скидки: цены/права по-прежнему определяет billing.

Для персональных сообщений исключить утечку между аккаунтами, общий HTTP cache,
перебор чужих message ID и подделку ACK. Нужны серверные тесты авторизации,
сроков/аудиторий/редакций/идемпотентности и интеграционная приёмка двумя клиентами.
Не журналировать access tokens и персональный текст сообщения. Получение списка
не должно записывать прочтение и не должно обновлять last_login_at.

Возможные будущие политики «на каждое устройство» или периодические напоминания
определяются сервером отдельно; V1 не реализует управление ими. При одновременном
входе до ACK окно может появиться на обоих устройствах. Exactly-once показ и
мгновенное закрытие уже открытого окна другого устройства не обещаются.

Управление сообщениями сначала можно сделать служебной командой/закрытым API,
затем административной страницей. Push и доставки уже работающим клиентам,
внешние ссылки/изображения и новая UI-схема — отдельные согласованные этапы.

## Проверка

Unit tests проверяют схему, fallback, HTML как текст, auth/query/ACK/timeout,
новый/восстановленный вход, отсутствие API, очереди/сроки/другие modal-окна,
смену аккаунта, «позже», повтор ACK и переход только после подтверждения.
Тест независимых клиентов использует общий fake backend и не доказывает
работу настоящего backend. Native capture включает явный --simulate-messages
loopback fixture: обновление, ошибка ACK, повтор и предложение с переходом.
По умолчанию fixture messages API не предоставляет. Реального backend,
персональной рассылки и синхронизации устройств этой задачей не проверено.
