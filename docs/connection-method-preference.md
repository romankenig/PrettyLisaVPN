# Подсказка подключения и запоминание способа

Android **0.13.0/code24 → 0.14.0/code25**, Windows **0.16.0 → 0.17.0**:
MINOR за новую локальную возможность. Backend **0.20.0 unchanged**, dashboard
**0.2.0 unchanged**, миграции не требуются. Продолжение PR #34; база до этой задачи
`f77b15eca2d098c2c850603ec997275d02790583`. Точные product/build SHA, run/attempt,
сборки, native screenshots, CI и фактический merge/deploy фиксируются в PR.

При CONNECTING оба клиента показывают краткую подсказку о паре минут для первого
подключения. Все шесть языков поддержаны; подсказка не обещает фиксированный срок
и скрывается после окончания/отмены. Сообщения о конкретных попытках сохранены.

Единый executor сначала берёт последний успешный method ID, если адаптер всё ещё
доступен, затем остальные адаптеры в исходном порядке без повторения. Неизвестный
или повреждённый ID игнорируется. Если сохранённый способ не сработал, обычный
fallback продолжается только после его очистки. Успех требует Internet verification,
сохраняется до перехода CONNECTED; отменённый или устаревший результат не сохраняется.

Предпочтение принадлежит установке приложения, общее для стран и входов на этом
устройстве. Android использует приватные SharedPreferences (`vpn-method`), Windows —
существующее WebView localStorage (`prettylisavpn:last-successful-vpn-method`).
Сохраняется ровно ID, без аккаунта, страны, IP, ключей и истории. Logout не очищает
несекретное предпочтение; очистка данных/удаление приложения сбрасывает его.
Ошибка хранилища оставляет рабочее подключение и выбор в памяти процесса.

Тесты проверяют повторный запуск с сохранённым ID, отказ предпочитаемого способа,
порядок и отсутствие дублей, неизвестный ID, отсутствие записи после неуспеха,
отмены/смены владельца, недоступное хранилище. Нативные UI-сценарии проверяют
подсказку на Windows/Android. Это проверки orchestration/UI, не новое доказательство
реального подключения для нового APK. API и криптография этой задачей не меняются.

Клиентский откат независим: предыдущие приложения игнорируют новое предпочтение
и начинают с прямого WireGuard. Backend follow-up не нужен. Для merge стека сначала
#34 в ветку #33, затем объединённый #33 в develop: автоматический development deploy
должен получить всю уже применённую серверную схему 0032, а не старую 0030.
